## 1. 요약

에이전틱 캐릭터 공장은 사용자가 쓴 기획 브리프 한 장을 받아 캐릭터 한 명의 전체 자산을 만든다. 자산은 외모(레퍼런스 근거, 고른 얼굴과 기준 사진, 외모 명세), 기획(이름·직업·성격·세 챕터), 영상(챕터 기준 프레임, 소개 영상, 액션 영상 세트), 페르소나(상세 특질, 긴·짧은 프롬프트), 학습(SFT 데이터, 학습 결과, 비교 평가)과 이들을 ID로 묶은 릴리즈 매니페스트다.

지금은 사람이 Pinterest·Instagram·웹에서 레퍼런스를 찾고, 이미지 모델로 대표 이미지를 만들고, 기획을 적고, 영상 모델에 넣고, 페르소나와 학습 데이터를 따로 설계한다. 공장은 그 탐색·선별·기획·생성·검사·반복을 단계별 에이전트가 수행하게 하고, 사람은 정해진 관문에서 후보를 고르고 승인하는 역할로 바꾼다.

첫 릴리스 R0는 전 공정을 완성하기보다 두 질문에 답한다. 첫째, 레퍼런스 선별을 인기의 근거와 비교 조건이 남는 방식으로 에이전트가 수행할 수 있는가. 둘째, 얼굴 선택→기준 사진→기획→챕터 프레임→특질→프롬프트까지의 산출물이 사람의 승인을 받을 만한 품질로 반복 생산되는가. 영상 생성, SFT 학습, 릴리즈 실행은 R1이다.

## 2. 배경과 문제

### 2.1 현재 공정에서 사람의 탐색·선별이 병목이다

출발 핸드오프 §2에 적힌 원래 공정은 이미지·영상 6단계와 페르소나·SFT 5단계다. 첫 단계인 레퍼런스 탐색은 사람이 직접 Pinterest·Instagram·웹을 돌며 "예쁜 캐릭터"를 찾는다. 이 작업은 시간이 많이 들고, 결과가 사람의 취향에 묶이며, 왜 그 외모를 골랐는지 근거가 남지 않는다.

### 2.2 외모 선택에 근거가 없다

사용자는 "예쁜 이미지를 찾아오는 것"이 아니라 "잘나가는 외모를 어떤 근거로 골라올지"를 핵심으로 본다(출발 핸드오프 §1). 현재는 선택 이유를 재현하거나 비교할 수 없어, 캐릭터가 서비스에서 반응을 얻지 못했을 때 외모 선택이 문제였는지 다른 요인이었는지 가릴 수 없다.

### 2.3 자산이 흩어지고 ID가 맞지 않는다

대표 이미지, 세 배경, 소개 영상, 액션 영상, 긴·짧은 프롬프트, 학습 모델이 서로 다른 도구와 폴더에 생기며, 어떤 프롬프트 버전이 어떤 영상·모델과 짝인지 손으로 맞춘다. 릴리즈 때 `character_id`·`persona_version`·영상 ID를 맞추는 작업이 별도 공정으로 남아 있다.

### 2.4 페르소나와 학습 데이터 설계가 미완이다

`gemini-sft-poc`에서 SNS 재작성 파일럿, 14유형 분류, 선택 학습 기준, 짧은 페르소나 정렬 원칙이 만들어졌지만, 새 캐릭터에 적용하는 절차는 문서마다 흩어져 있고 한 번의 공정으로 묶이지 않았다. 상세 페르소나 생성과 학습 데이터 구성에는 아직 설계할 부분이 있다(출발 핸드오프 §2).

### 2.5 "완료"가 확인되지 않은 채 보고된 적이 있다

출발 핸드오프 §6은 시각화 도구의 로그인·보드 생성 성공을 편집 가능 상태로 잘못 설명한 사례를 기록했다. 공장은 연결·설치·요청 반환이 아니라 실제 산출물과 검사 결과로 완료를 판정해야 한다.

## 4. 제품 범위

입력은 `brief-v1` 하나다. 타깃·그림체·외모 범위, 레퍼런스 출처, 세 챕터와 액션 목록, 페르소나 방향, 예산·해상도 제약을 담는다. 양식은 [brief-template.md](../templates/brief-template.md)다.

출력은 `release-manifest-v1`과 그것이 가리키는 자산이다.

| 자산군 | 산출물 |
|---|---|
| 레퍼런스 | 화제성 순위 목록, 인물별 외모 특징 태그, 외모군 후보와 인기 근거 보고서, 외모군별 얼굴 미리보기 |
| 외모 | G1에서 고른 얼굴과 선택 기록, 기준 사진과 자동 동일인 검사 기록, 외모 명세(`appearance-spec`) |
| 기획 | 기획 씨앗, 상세 변형과 선택 기록, 이름·직업·성격·선택·말투·프로필 카드·챕터 관계 흐름이 든 기획서(`character-plan`), 참고 자료 묶음(`reference-set`) |
| 장면 | 챕터별 배경 후보와 배경 사진, 챕터 사실(장면 사실·만남 경위·관계 정본·장면 경계), 자세·의상 |
| 영상 | 챕터 완성 이미지 3장(9:16), 소개 영상, 액션 영상 세트와 검사 결과 |
| 페르소나 | 상세 특질 시트, 긴 프롬프트, 짧은 프롬프트(`persona_version`) |
| 학습 | 데이터 revision(학습·검증·평가 분할), 학습 결과, 비교 평가 보고서 |
| 릴리즈 | 모든 ID와 해시를 묶은 매니페스트 |

## 5. 사용 장면

### J1. 첫 캐릭터 전체 공정 (R0 일부, R1 완성)

1. 기획자가 브리프를 쓴다. 미정 항목은 "미정"으로 남긴다.
2. Scout가 화제성 순위 목록의 인물을 외모 특징 태그로 바꾸고, 공장이 여러 명이 공유하는 특징으로 외모군 후보·인기 근거 보고서·외모군별 얼굴 미리보기를 만든다(D-0017). 기획자가 관문 G1에서 얼굴 한 장을 고른다. 고른 얼굴이 외모군을 정하고, 외모를 고르는 사람 관문은 G1 하나다(D-0042).
3. Stylist가 고른 얼굴로 기준 사진을 만들고, 자동 동일인 검사가 G1 얼굴과 같은 사람인지 확인한다. 통과하면 공장이 외모 명세를 고정한다. 이 단계에는 사람 관문이 없다. 어긋나면 자동으로 다시 만들고, 끝까지 어긋나면 멈추고 기획자에게 알린다(D-0042).
4. 외모 명세가 고정되면 기획자가 기획 씨앗(대표 성격·직업·나이·성별·간단한 배경)을 쓴다. 그동안 소개 영상이 만들어진다(D-0033). Planner가 같은 씨앗으로 상세 변형 3안을 만들고, 기획자가 G3에서 한 안을 고르거나(칸 수정 가능) 직접 쓴 상세안을 정리한 안을 고른다. 기획서가 고정되면 Curator가 참고 자료 색인에서 쓸 자료를 사람을 기다리지 않고 고른다.
5. Location Scout가 챕터마다 배경 후보 3개와 인물 없는 9:16 배경 사진을 만든다. 기획자가 G4a에서 챕터마다 고르거나 원하는 배경을 한두 줄로 정의한다. Scene Writer가 고른 배경으로 챕터 사실을 이어서 쓰고, Pose Director가 배경마다 자세·의상 후보 3개를 낸다. 기획자가 G4b에서 고르거나 직접 정의하거나 세부를 고친다. Framer가 기준 얼굴·배경 사진·자세로 챕터 완성 이미지 3장을 만들고, 기획자가 G4에서 챕터마다 승인하거나 수정을 요청한다(D-0033, D-0034).
6. Director가 외모 명세의 기준 사진으로 소개 영상을 만들고 기획자가 G5에서 고른다(R0, D-0028). G4가 승인되면 Director가 챕터 완성 이미지를 첫 프레임으로 앱 통화 영상과 같은 이름의 동작 영상(대기·감정 반응, 장면 소품을 쓰는 특별 행동)을 만들고, 기획자가 G5b에서 동작마다 고르거나 빼거나 다시 만들게 한다(R1, D-0038, D-0040). 얼굴·손·루프 자동 검사는 나중에 붙인다.
7. Profiler가 기획서와 기준 문서로 상세 특질 시트를 만들고, Prompter가 긴·짧은 프롬프트를 만든다. 기획자가 G6에서 승인한다. `persona_version`이 발급된다.
8. (R1) DataSmith가 SNS 재작성·NIKL 보강·합성 장면으로 데이터 revision을 만들고 표본 검수를 받는다(G7). Trainer가 학습하고 비교 평가 보고서를 낸다(G8).
9. (R1) Releaser가 매니페스트를 만들고 기획자가 G9에서 릴리즈를 승인한다.

### J2. 레퍼런스 선별 소규모 실험 (R0)

타깃·그림체 하나와 화제성 순위 목록(인물 20~40명, 제안)으로 외모군 3~5개(제안)를 만들고, 인기 근거와 비교 조건이 보고서에 남는지, 특징 추출부터 다시 돌려도 같은 군집이 나오는지, 다음 단계 산출물에 인물 이름이 남지 않는지 확인한다. 서비스 썸네일 비교는 R2까지 외부 지표 파일 import로만 둔다(Q-0012).

### J3. 기존 캐릭터의 영상 증보 (R1)

이미 G4 승인 이미지가 있는 캐릭터에 동작 목록을 추가하거나 바꿔 S6만 다시 돌린다. 새 revision에서 동작마다 `action_id`(챕터-동작), 영상마다 `video_id`가 발급되고 매니페스트가 새 revision으로 갱신된다.

### J4. 페르소나 개정과 재학습 (R1)

특질 시트나 프롬프트를 고쳐 새 `persona_version`을 만들고, 같은 평가 세트로 이전 버전과 비교한다. 외모·영상 자산은 그대로 둔다.

## 10. 비목표

- 서비스 런타임(chat-svc 등)의 프롬프트 조립, 과금, 배포를 바꾸지 않는다.
- 평가 결과로 캐릭터를 자동 릴리즈하지 않는다.
- 레퍼런스 출처의 이용 약관을 넘는 자동 수집을 하지 않는다. 접근이 허용된 API나 사용자가 직접 저장한 자료만 쓴다.
- 레퍼런스 이미지를 그대로 복제하는 생성을 목표로 하지 않는다. 외모군의 특징을 참조한다.
- 실존 인물의 이름을 이미지 생성 입력에 넣지 않는다. 특정 인물을 재현하는 생성을 목표로 하지 않는다(D-0017).
- R0에서는 영상 생성, 학습, 릴리즈, 서비스 지표 연동을 실행하지 않는다.
- 캐릭터의 음성 합성을 다루지 않는다.

## 14. 수용 조건 요약

R0는 다음을 모두 만족하면 끝난다.

1. 합성 자료와 가짜 공급자로 S1~S11 전체 흐름이 네트워크 없이 통과한다.
2. 실제 순위 목록으로 S1을 돌려 G1 보고서가 §6의 선별 근거·이름 분리 지표를 만족한다(사용자 지시 뒤).
3. 실제 모델로 S2~S4, S7~S8을 돌려 S2 자동 검사 기록과 G3·G4·G6 승인 기록이 한 캐릭터에 대해 모두 남는다(사용자 지시 뒤).
4. 원장만으로 R0의 비용 보고서가 만들어진다.
5. 인계 문서가 규칙대로 남아 다음 세션이 R1을 시작할 수 있다.

PoC(D-0044)는 다음을 모두 만족하면 끝난다. 자세한 기준은 [PoC 계획서](2026-10-27-poc-plan.md) §8이다.

1. 여성·남성 합성 브리프 두 개가 가짜 공급자로 S1 → G9 → 패키지 → 우리 앱 일회용 DB 적재까지 네트워크 없이 통과한다.
2. 같은 흐름을 워크숍 화면에서 관문만 눌러 끝까지 간다.
3. 모든 실제 어댑터가 dry run과 계약 테스트를 통과하고, 순위 수집·이미지·LLM은 실제 1회 호출로 산출물이 계약에 맞는다(사용자 실행 지시 뒤).

## 20. 공식 API 직접 연결과 호출 비용 기록(2026-11-04, D-0079)

### 20.1 문제

시연은 학습 없이 캐릭터 프롬프트 경로(S3 → G3 → S7 → S8 → G6)로 캐릭터를 만든다. 이 경로의 텍스트 호출은 지금 로컬 중계(opencodex)를 거친다. 중계는 구독으로 과금되므로 원장의 비용 칸이 모두 0으로 남고, 캐릭터 한 명을 만드는 데 드는 API 비용을 측정할 수 없다.

공식 API로 바로 바꾸는 것도 현재 구조로는 되지 않는다. 텍스트 모델 덱은 GPT와 Gemini를 섞어 쓰지만 호출 경로마다 주소와 키를 하나씩만 받는다. 모델 이름은 중계 전용 이름(`google-antigravity/...`)이다. GPT-6.1 계열은 추론 강도를 켜면 `temperature`를 거절하는데, 공장은 모든 요청에 `temperature`와 지원 중단된 `max_tokens`를 보낸다. 원장에는 단가가 없어서 비용을 계산하지 못하고, 새 형성 경로의 실행 예산은 단가가 없으면 실제 호출 전에 거절한다.

### 20.2 사용 장면

1. 사용자가 저장소 루트의 `.env`에 OpenAI와 Gemini 키를 넣는다.
2. 사용자가 호출 경로를 `api`로 고르고, 호출 계획(dry run)에서 예상 호출 수와 비용 상한을 확인한다.
3. 사용자의 실행 지시 뒤 공장 화면이나 명령으로 시연 경로를 한 캐릭터만큼 돌린다. 사람은 G3과 G6에서 고르고 검토한다.
4. 사용자가 비용 보고서로 단계별·모델별 비용을 보고, 각 회사의 사용량 화면에 나온 청구액과 비교한다.
5. 사용자가 과거 중계 실행 기록에도 같은 단가표를 적용해 API로 돌렸다면 얼마였을지 본다.

### 20.3 목표와 지표(제안)

| 목표 | 지표 |
|---|---|
| 시연 경로 한 캐릭터의 텍스트 비용을 단계별로 안다 | 시연 경로의 모든 텍스트 호출에 비용 또는 "단가 미확인" 표시가 남는다. 비용 칸이 비어 있는 이유 없이 0으로 남은 호출은 0건이다. |
| 기록한 비용이 실제 청구와 맞는다 | 첫 실제 실행에서 원장 합계와 회사별 사용량 화면의 차이가 ±10% 안이다(제안). 차이가 크면 원인을 Q-0023으로 추적한다. |
| 공식 API 호출이 형식 오류로 멈추지 않는다 | 첫 실제 실행에서 요청 형식 때문에 거절된 호출이 0건이다. |

### 20.4 기능 요구사항

| ID | 요구사항 | 수용 조건 |
|---|---|---|
| FR-65 | 텍스트 모델 덱에 공식 API 호출 경로(`api`)를 두고, 모델 계열마다 주소와 인증 환경변수를 따로 적용한다. | GPT 계열은 OpenAI 공식 주소와 `OPENAI_API_KEY`로, Gemini 계열은 Gemini API의 OpenAI 호환 주소와 `GEMINI_API_KEY`로 호출한다. 중계 전용 모델 이름은 공식 모델 ID로 바꿔 보낸다. 키가 비어 있으면 첫 호출 전에 거절한다. 실패해도 다른 계열·경로·모델로 자동 대체하지 않는다. 기존 opencodex·test 경로와 프로필 선택(FR-59)은 그대로 쓸 수 있다. |

| FR-68 | 실행 예산과 호출 계획이 같은 단가표를 쓴다. | 형성 실행 예산의 단가 상한은 지금 선택한 프로필·경로가 쓸 모델들의 단가 가운데 가장 높은 값으로 잡는다. 쓸 모델 가운데 단가가 없는 것이 있으면 실제 호출 전에 거절한다. 설정에 단가를 직접 적으면 그 값이 우선하고, 덮어쓴 사실이 원장에 남는다. |
| FR-69 | 원장으로 비용 보고서를 만들고, 과거 기록에도 단가표를 적용해 볼 수 있다. | 보고서는 단계·모델·과금 구분별 호출 수, 토큰, 비용, 단가 미확인 호출 수를 보인다. 과거 기록 재계산은 원래 원장을 고치지 않고, 중계로 돈 호출은 "API 환산"으로 표시한다. |

비기능 요구는 기존 NFR-05(비밀값), NFR-08(오프라인 테스트), FR-03(유료 호출은 `--execute`와 사용자 지시)을 그대로 따른다. 키 값은 원장, 오류 문구, 보고서, 화면 응답에 남기지 않는다.

### 20.5 비목표

- 이미지 생성(Codex 구독)과 S1·S4a의 `codex exec` 실행 비용은 측정하지 않는다. 이 단계들은 API를 부르지 않는다.
- 영상(xAI)과 GPU 학습 비용 기록은 바꾸지 않는다. 이미 각자의 단가 계산이 있다.
- Anthropic 공식 API 연결, Responses API 전환, 스트리밍, Batch API, 프롬프트 캐시 최적화는 이번 범위에 넣지 않는다.
- 모델 배정과 프로필(FR-58)은 바꾸지 않는다.
