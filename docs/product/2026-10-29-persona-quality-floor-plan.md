# 페르소나 형성 공정의 기본 품질 확보 계획

> **For agentic workers:** REQUIRED SUB-SKILL: 구현을 시작할 때 superpowers:executing-plans 또는 superpowers:subagent-driven-development를 사용한다. 이번 요청은 계획 수립과 서브에이전트 검토까지다. 구현·모델 호출 실험·학습 제출·커밋은 이번에 하지 않는다.

**Goal:** 지원 범위의 새 캐릭터를 같은 공정으로 만들면, 개별 문장 수정이나 좋은 응답 재추출 없이 일정 이상의 대화 품질이 나오는 형성 과정을 만들고 검증한다.

**Architecture:** 승인 기획 → 상황별 행동·목소리 설계 → 자연스러운 다중 턴 예시 형성 → 정본을 보존하는 프롬프트 컴파일을 고정 공정으로 만든다. 공정과 소비 모델을 고정한 뒤 개발에 쓰지 않은 캐릭터에서 첫 완성품의 품질선을 검증한다. 평가가 끝난 캐릭터만 고쳐 합격시키는 방식은 성공으로 세지 않는다.

**Tech Stack:** 기존 Python 3.12·Pydantic·httpx·pytest·cfp·로컬 opencodex 중계. 새 UI나 새 사람 승인 관문은 추가하지 않는다.

**Spec:** 현행 [PRD FR-19~23](prd.md), [명세 §10](../architecture/spec.md), [LLD §8.3·§8.6·§8.7](../architecture/lld.md)에 기반한 **설계·실행 제안**이다. Task 0에서 이 계획을 반영할 PRD→spec→LLD 개정과 측정 규약을 먼저 고정한다.

## 1. 목표와 현재의 차이

사용자가 원하는 것은 “차은결을 여러 번 고치면 좋아진다”는 시연이 아니다. **페르소나 형성이 끝난 산출물 자체가, 지원하는 대화 모델·채널에서 개별 손질 없이 사용할 수 있는 최소 품질을 갖추는 것**이다.

현재 확인한 범위는 다음과 같다.

- `source.py`는 신원·생활·말투·챕터 전달 누락을 해결했다. 구형 v1·길이 상한·재개도 오프라인 검사로 보완했다.
- 차은결 pv2는 새 누적67턴·기존 이력 고정40턴에서 호감·경청이 개선됐다. 다른 새 캐릭터의 재현성 근거는 없다.
- S7의 trait-sheet-v1은 선택·경계 중심이며, 규칙을 적용하지 않을 조건과 일상 대화 기반을 구조적으로 보장하지 않는다.
- S8은 긴·짧은 프롬프트와 독립 단문 probe를 만들지만, 생성 시점에 자연스러운 대화 흐름을 형성하는 단계가 없다.
- 한소민 r3는 원본 말투 기반361대화와 이력·주체·갈등 보강을 포함한644대화·3,977답변을 학습했다. 문구나 비율만 복사할 근거는 없고, 어떤 요소 하나의 효과를 분리한 실험도 아니다.

근거는 [첫 품질 시험](../reports/2026-10-28-persona-quality.md), [한소민 분석·개선](../reports/2026-10-29-somin-transfer.md), K-0042·K-0043·K-0045·K-0046이다.

## 2. 지원 범위와 보장의 뜻

첫 품질 프로필은 `ko-text-prompt-long-v1`로 제한한다.

- 현대 한국 배경의 성인 연애 대화 앱 캐릭터, 한국어 문자 대화를 지원한다. 성별·직업·나이·성격·관계 거리의 범위를 서로 다르게 검증한다.
- 소비 모델은 실행 직전 확인한 서비스 기본 대화 모델을 쓴다. 현재 설정은 Gemini 3.8 Flash다. 모델명·제공자 경로·추론 설정·temperature·길이·system 조립 버전·컨텍스트 제한을 함께 고정한다. 중계의 내부 revision을 모르면 미확인이라고 기록한다.
- long 프롬프트만 첫 품질 보장 범위에 넣는다. short·음성·다른 언어·다른 모델·SFT는 별도 프로필로 검증하기 전까지 미검증이다. D-0006·G8의 short 미채택 원칙은 유지한다.
- “보장”은 지원 범위·동결된 공정·공개한 기준·관측한 첫 완성품 성능을 뜻한다. 소수 표본으로 모든 미래 캐릭터나 모든 대화를 확률100%로 보장하지 않는다.
- 지원 범위를 벗어나거나 필수 정보가 서로 모순된 입력은 이유를 내고 멈춘다. 정상 입력을 실패 뒤에 범위 밖으로 재분류해 분모에서 빼지 않는다.

## 3. 선택한 개선 방식

| 대안 | 기대와 한계 | 선택 |
|---|---|---|
| 금지 문구·자동 판정을 늘린다. | 알려진 오류를 가릴 수 있지만, 생활·말투·대화 흐름의 기반이 약한 원인은 남는다. | 주된 개선 방식으로 쓰지 않는다. |
| **상황별 성격 설계와 자연 대화 예시 형성을 공정에 넣는다.** | 기존 정본 보존에 판단의 적용 범위와 목소리의 실제 흐름을 더한다. SFT의 성공 방법을 활용하지만 학습 효과를 재현했다고 주장하지 않는다. | **이번 구현의 기본 방향으로 제안한다.** |
| 바로 캐릭터별 SFT를 학습한다. | 체화된 말투를 얻을 여지는 있지만, 부실한 페르소나·예시를 학습하면 결함도 고정된다. 현재 실행 범위에 학습 제출은 없다. | 별도 분기로 둔다. 두 번의 공정 개선 후 개발 기준을 못 넘으면 prompt-long의 한계를 기록하고 데이터·학습 계획으로 전환한다. |

평가기는 공정의 품질을 확인하는 수단이다. 출력을 수십 번 뽑아 좋은 것만 고르는 수단으로 쓰지 않는다. 형성용 예시는 나중의 S9가 재사용할 수 있지만, S9→S7 역의존이나 학습 승인을 형성 공정에 끼워 넣지 않는다.

## 4. 형성 공정 변경

### 4.1 S3: 일상에서도 작동하는 기획

기존 character-plan-v1/v2는 읽을 수 있게 유지한다. 새 기획 지침은 다음을 함께 요구한다.

- 선택과 우선순위는 같은 상황의 첫 행동으로 구분한다.
- 선택·거절이 필요 없는 평범한 상황에서 자기 이야기·취향·관심을 꺼낼 생활 재료를 만든다.
- 원하고 두려워하는 것은 모든 말을 의심하거나 선 긋는 이유로 만들지 않는다.
- 말투 예시는 어미만 바꾼 문장이 아니라 일상·감정·갈등의 온도 차이가 보이게 한다.

검증은 씨앗부터 시작한다. S3는 한 호출로3안을 만들고 G3에서는 사전 고정한 `v1`을 선택하는 시험 규약을 기존/신규 공정에 동일 적용한다. 후보 전체·선택 규칙·결정을 보존하며 칸 수정·후보 재추출·대화 결과를 보고 선택 변경은 하지 않는다. 이 증거의 범위는 이 선택 규약까지 포함한다. 실제 운영에서 다른 선택·수정을 쓰면 같은 프로필 증거로 자동 간주하지 않는다.

LLM 의미 검토로 정본을 임의 수정하지 않는다. 구조 부족·모순은 단계 실패로 남기고 첫 결과를 보존한다.

### 4.2 S7a: 행동·목소리 설계

`persona-blueprint-v1`을 새 계약으로 추가한다. 새 프로필의 S7a는 승인 기획에서 **trait-sheet-v1 호환 본문과 blueprint를 한 모델 호출로 함께 생성**한다. 공장이 특질 본문 해시를 계산해 두 산출물을 묶는다. 별도 trait 생성 뒤 blueprint를 다시 생성하지 않는다. 기존 공정은 구형 경로를 유지하며 기존 sheet를 새 프로필로 조용히 승격하지 않는다.

- `sourceRefs`: 승인 기획·특질·허용된 기준 자료의 버전과 해시를 남긴다.
- `decisionRules[]`: `situation`, `activateWhen`, `doNotActivateWhen`, `firstMove`, `priority`, `switchWhen`, `wrongTransformation`을 명시한다. “호감≠확답 압박”, “새 일정≠틀린 회상” 같은 구분은 캐릭터와 무관한 사실 처리 원칙과 나눈다.
- `voiceProfile`: 기본 말높임·문장 호흡·직접성·감정별 변화·관계별 거리·적합한 어휘와 피할 반복을 적는다. 한소민의 애교·직업·배경을 기본값으로 넣지 않는다.
- `ordinaryModes`: 반응만 하기·자기 이야기·장난·경청·호감 표현을 어떻게 고르는지 적는다. 모든 모드를 매 턴 실행하게 하지 않는다.
- `factPolicy`: 자기 허구와 사용자 사실·공동 과거·제안/합의/취소·외부 현재 사실의 범위를 분리한다. 허구 자기 일정을 절대 사실로 만들어 이후의 명시적 변경을 막지 않는다.
- `unresolved[]`: 알 수 없는 필드를 새 정본으로 채우지 않는다. 필수 결손과 선택적 미정의 처리를 나눈다.

### 4.3 S7b: 자연스러운 다중 턴 예시 형성

`formation-dialogues-v1`을 **정규 형성 산출물**로 만든다. 평가 응답을 보고 캐릭터별로 고치는 단계가 아니다.

- 캐릭터당12대화, 각각2~6쌍의 user/assistant를 제안한다. 일상·자기 이야기·가벼운 장난·호감8개, 하소연/거절/갈등2개, 조건·책임 주체 변경2개로 시작한다. 두 대화 이상은6쌍으로 한다. 이 비율은 최적값이 아닌 첫 개발값이다.
- 목표는 말투 장식이나 늘 같은 마무리가 아니라 주고받는 흐름이다. 약속을 정한 뒤 다른 이야기로 이어가고, 질문·정정이 없으면 합의 시간을 계속 붙이지 않는다.
- 예시의 가상 사용자 사실·공동 사건은 `example-local`로 표시하고 실제 캐릭터 정본에 합치지 않는다. 정본·이력·판단·표현의 출처를 남긴다.
- 평가 입력·평가 루브릭·보류 캐릭터는 예시 작성 모델에 주지 않는다. 기존 한소민·SNS 원문을 대사나 사실로 복사하지 않는다.
- 형식 재시도는 최대2회다. 의미상 품질 때문에 같은 예시를 다시 뽑아 선별하지 않는다. 부족하면 해당 공정 버전의 실패로 기록한다.

### 4.4 S8: 고정 컴파일과 사용 계약

- `persona-bundle-v1`에 blueprint·예시·정본·compiler·시스템 규칙·소비 프로필의 해시를 묶는다.
- 정본 직접 조립을 유지한다. long system에 `CHARACTER_EXAMPLES` 섹션을 추가하고, 예시임을 명시한 짧은 대화4개를 **고정 슬롯(일상·자기 이야기, 장난·호감, 경청·갈등, 조건·주체 변경)별 첫 ID 순서**로 고른다. 품질 점수로 좋은 것만 고르지 않는다. 나머지8개도 산출물에서 보존한다.
- 예시는 실제 세션 이력이 아니다. 실제 messages에는 고정 system + 누적 실제 대화 + 현재 user만 넣는다. 예시의 사용자 사실이나 약속을 실제 대화에 가져오지 않는 회귀 시험을 둔다.
- long 전체 상한은 첫 제안8,000자다. 정본과 필수 예시를 담을 수 없으면 명시적으로 실패시키며 조용한 절단·프롬프트 길이 임의 확대는 하지 않는다. short는 기존2,400자 상한을 유지하고 별도 미검증으로 둔다.
- 임베드 예시가8,000자를 넘어도 기준을 맞추려고 그때그때 개수를 줄이지 않는다. 최소4개를 넣는 고정 컴파일 규칙 자체를 개발셋에서 고친 뒤 버전을 바꾼다.

컴파일은 모델 호출0회다. 정본 네 섹션은 기존 직접 투영을 유지하고, 행동 섹션은 `decisionRules`, 말투는 `voiceProfile`, 일상 흐름은 `ordinaryModes`, 사실 처리는 `factPolicy`에서 버전 고정 템플릿으로 직렬화한다. 불변 신원·핵심 설정은 정본을 기준으로 하며 사용자 주장만으로 덮어쓰지 않는다. 일정·합의·관계 등 변경 가능한 상태는 실제 이력에서 확인된 최신 변경 > 정본의 초기 상태 > 행동/표현 예시 순으로 처리한다. blueprint와 예시가 불변 정본이나 실제로 확인된 상태 변경을 덮어쓰지 못한다. 정확한 섹션 매핑·빈 필드 처리·순서를 Task 0의 LLD에 적는다.

FR-21의 long/short 동일 섹션 조건은 프로필별 상태를 허용하도록 Task 0에서 개정한다. 새 `prompt-pair-v2`는 `long=READY`, `short=UNAVAILABLE|UNQUALIFIED|READY`를 구분하며 long-only 형성을 short 실패로 무효화하지 않는다. short 산출물은 별도 프로필에서만 생성하고 사용 승인한다. v1을 허위로 채우지 않으며 구형 소비자는 v1 그대로, 새 소비자는 v2의 long을 읽는 명시적 어댑터를 쓴다. short 필수 소비자는 미지원 사유로 멈춘다.

### 4.5 실행·상태·관문

`S7a blueprint → S7b examples → S8 compile → 기존 G6`로 이어간다. 구현상 s7이 두 하위 작업을 책임지고, s8은 새 bundle이 완성됐는지 확인한다. 새 사람 관문은 만들지 않는다.

- 형성 완료는 bundle이 완전하고 해당 프로필에 적합한 상태다. G6 사람 승인은 기존처럼 별도다.
- 개별 품질 검사로 자동 재생성·문장 교정을 돌리지 않는다. 공정 개선에 쓰는 오류는 다음 공정 버전에 반영한다.
- `FORMED`를 곧 전 모델·전 채널의 품질 보장으로 해석하지 않는다. `recipeQualification`은 별도 프로필 증거를 참조한다.
- 구조 실패·정본 모순·모델/도구 실패는 `CHECK_FAILED`로 남기고 상한 내 재개한다. 완성품을 얻지 못한 정상 입력도 공정 첫 통과율에서 실패다.
- G6 승인은 bundle 해시와 정확한 S7 revision·12개 예시·prompt-pair를 함께 고정한다. 승인 처리·관문 검토 입력·`persona-version.json`·S9/패키지의 읽기 경로를 버전 인식 로더로 연결한다. v1은 기존 경로로 읽고 v2는 승인 bundle에서 long을 투영하며 “최신 파일”로 바꿔치기하지 않는다.
- 기존 v1만으로 구성된 과거 G6는 그대로 열 수 있다. 새 bundle이 없는 과거 산출물을 새 프로필 합격으로 소급하지 않는다. 중단 재개는 저장된 revision·예시·프롬프트를 재사용한다.

## 6. 검증 설계와 실패 시 처리

### 6.1 개발·보류 분리

- 개발 캐릭터4명은 현재 차은결을 포함하고 성격이 다른3명을 새로 정한다. 공정 수정과 판정 교정은 여기서만 한다.
- 보류 캐릭터8명은 독립 검토자가 직업·성별·나이·주도성·친밀감 표현·갈등 반응을 분산해 정한다. 개발 캐릭터의 이름만 바꾼 안은 금지한다. 실행 전 입력·시나리오·출처·분리 근거를 해시로 고정한다.
- 공정 동결 전 생성·개선 담당에게 보류 원문을 주지 않는다. 생성 모델은 해당 캐릭터 브리프와 단계 산출물만 보고, 평가 사용자 턴은 bundle 동결 뒤 대화 모델에만 넣는다.
- 보류에서 공정을 고치면 그8명은 다음의 개발 근거가 된다. 새 보류8명과 새 상황을 준비하지 않으면 “처음 보는 캐릭터의 통과”라고 부르지 않는다.
- 실행 전16개 고정 슬롯(character×run)을 등록한다. JSON 파싱·필수 필드 형식만 최대2회 재시도할 수 있고 모든 시도를 보존한다. 의미상 수정·정본 모순 수정·단계 재생성·슬롯 교체는 첫 통과 실패다. 실패 후 재개 성공은 복구 지표로만 보고하며 첫 통과를 바꾸지 않는다. 출력 없는 전송 실패도 슬롯 실패로 남기며 미완성 슬롯은16개 분모에서 제외하지 않는다.
- 독립 검토자는 개발 장면·기존 probe·형성 예시와 보류 문제의 의미상 중복을 확인하고 분리 근거를 남긴다. 공통 오류 영역의 중복과 구체 상황·정답 행동의 재사용을 구분한다. 형성 후 구체 중복이 발견되면 해당 시험을 독립성 미달 `NOT_QUALIFIED`로 기록하며, 결과를 보고 문제를 바꿔 같은 시험을 재채점하지 않는다.
- 독립2회는 같은 정상 입력으로 공정을 처음부터 각각 실행하는 두 run이다. 제공자가 생성 seed를 지원하지 않으면 입력 선택 seed와 run ID만 고정하고 모델 출력 재현성을 가장하지 않는다. 두 run 모두 보존한다.

### 6.2 실제 대화

산출물당6장면×6사용자 턴=36턴, 별도 연속24턴=24턴으로 총60응답을 제안한다. 일상·가벼운 감정/장난·하소연·호감 진전·갈등/회복·조건/주체 변경을 다루며,24턴에는 평범한 대화 후 조건 변경과 갈등이 온다. 상황당 첫 행동5개는 이60턴 안의 사전 지정 위치에서 확인한다. 대조 캐릭터에는 같은 사용자 상황·관계·사전 사실 조건의 장면을 배정하므로 별도 응답 호출을 추가하지 않는다. 평가자는 승인 기획에서 기대 우선순위·허용 대안·상반 행동을 S7 생성 전에 봉인한다. 기획→blueprint 충실도와 blueprint→대화 구현도를 각각 판정하며, 기획과 충돌하는 blueprint는 응답이 설계대로여도 실패다. long의 최소 품질 검증이며 200턴 안정성은 별도 주장으로 남긴다.

시나리오는 고정 문장열만 쓰지 않는다. 사전 정의한 사실 상태(제안·합의·거절·취소·미정)와 분기표로 다음 사용자 턴을 선택한다. 실제 합의가 없으면 “합의했다”는 전제를 넣지 않고 거절/미정 분기를 탄다. 분기 해석도 recipe와 함께 동결하며 수작업 대사 변경을 금지한다. 총60턴은 유지하고 필요한 조건이 발생하지 않아 채점 불가능한 성격 문항은 성공으로 세지 않는다. 장면 자체는 자연스러움·오류의 분모에 남긴다.

모든 응답은 고정 system + 실제 누적 messages + 현재 user → 첫 assistant 하나다. 같은 답을 다시 뽑거나 고치지 않는다. 서비스 모델 설정·요청·응답·해시·실패·시간·토큰을 보존한다. 모델/연결 실패는 원래 실패로 남기고 품질 분모에서 조용히 제거하지 않는다. 응답이 돌아온 뒤의 재시도·잘린 응답 대체는 금지하고, 부분 출력은 실패다.

### 6.3 사람·LLM 판정

- 다른 계열 LLM은 결함 후보를 분류하고 원문의 정확한 인용을 준다. 사람은 후보 목록뿐 아니라 모든 평가 턴의 말투·주요 오류를 직접 표시한다. 주요 오류율은 주요 오류가 하나 이상 있는 assistant 턴 수/예정된 전체 assistant 턴 수로 계산하며 여러 오류를 한 턴에 중복 가산하지 않는다. 오류 유형별 사건 수는 별도로 공개한다. 점수 평균으로 합격시키지 않는다. 인용 불일치·미완료 JSON·규칙 오해를 표시한다.
- 보류16산출물의7장면 전체를 사람이 모델·공정 이름을 가린 상태로 읽는다. 한 장면의 전체 이력을 보고 판정한다. 각 산출물에서 짧은 장면1개와24턴 장면을 골라2개씩, 총32장면을 두 번째 사람이 독립 재검토한다. 두 평가자는 LLM 결함 후보를 보기 전에 판정한다. 장면 합격은 등급1 이상이며, 이중 평가의 이진 합격 일치율85% 이상을 제안한다. 미달이면 `NOT_QUALIFIED`로 기록하고 평가 신뢰도 미달 사유를 구분한다. 합격 여부를 바꾸는 모든 불일치는 별도 조정자가 원문 근거로 결정한다. 임계값과 추출 규칙은 개발 단계에 동결한다. 사람이 없으면 `METRICS_ONLY`이며 품질선 통과가 아니다.
- 판정 교정 예시는 개발 자료로만 만든다. 허구 자기 행동과 실제 외부 사실, 잘못된 회상과 새 조건, 질문에 답하는 재확인과 자발적 반복을 나눈다. 한소민도 모든 장면의 정답 캐릭터로 쓰지 않는다.
- 주요 오류의 종류·범위와 실패 산출물을 모두 공개한다. 일부 좋은 예문만 모아 보고하지 않는다.

### 6.4 기준선과 합격·반복

- 지금의 공정(pv2를 만든 소스·역할 프롬프트·규칙 해시)을 구현 전에 스냅샷으로 보존한다. 기존 미커밋 작업을 버리거나 자동 커밋하지 않는다.
- 개발에서는4캐릭터를 기존/새 공정으로 각각1회 만들어8산출물480응답을 비교한다. 이 비교와 동일 입력 단문은 원인 진단용이며 독립2회 성공의 근거가 아니다.
- 공정 동결 뒤 보류8캐릭터의 기존 공정1회=8산출물480응답, 새 공정2회=16산출물960응답을 수집한다. 절대 최소 품질선을 통과해야 하며 기존보다 낫기만 한 것은 합격이 아니다.
- 첫 보류 시험에서 미달이면 `NOT_QUALIFIED`다. 개별 수정으로 재통과시키지 않고 실패 유형을 공정에 반영한 다음 새 보류 세트로 검증한다.
- 개발 공정 개선은2회까지를 첫 예산으로 제안한다. 이후에도 기준을 못 넘으면 prompt-long만으로 충분하다고 주장하지 않고 자연 대화 기반 데이터와 SFT를 포함한 별도 계획으로 옮긴다. 학습 제출은 별도 명시적 실행 범위다.

## 8. 호출·비용·일정 제안

오늘은 계획·검토만 수행한다. 아래는 구현 뒤 **1회 개발 비교 + 1회 보류 시험**의 첫 추정이며 실제 dry run으로 다시 계산해야 한다.

| 항목 | 명목 호출 수 | 계산 |
|---|---:|---|
| 형성 생성 | 96 | 개발 기존4×3=12, 신규4×3=12, 보류 기존8×3=24, 신규16×3=48이다. 신규는 S3·S7a·S7b만 모델을 호출한다. |
| 대화 | 1,920 | 개발8산출물×60 + 보류24산출물×60이다. |
| LLM 분류 | 288 | 6개의6턴 장면 + 24턴을8턴씩3묶음, 산출물32개×9호출이다. |
| 명목 합계 | 2,304 | 96+1,920+288이다. |
| 재시도 포함 보수 상한 | 2,784 | 생성96×3 + 대화1,920 + 판정288×2다. 대화 재추출은0이다. |

생성96회는 기존 S3/S7/S8 각1회, 새 S3/S7a/S7b 각1회다. S3의3안은 한 호출의 출력이며 신규 S8은 결정적 처리0회다. 시험의 G3는 고정 ID 선택이므로 별도 추천 호출을 끈다. probe·이미지·관문 추천은 이 시험 경로에 포함하지 않으며 실제 dry run 원장과 이 산식이 다르면 실행 전에 정정한다.

대화 입력 평균3,000·출력200 토큰, 판정 입력12,000·출력3,000 토큰, 생성 입력8,000·출력5,000 토큰을 가정하면 명목 입력9,984,000·출력1,728,000 토큰이다. 이는 누적 이력을 포함한 평균의 가정이며 실제 모델 한도나 청구량을 확인한 결과는 아니다. 가정 단가가 입력100만 토큰당 $1~10·출력 $5~50이면 명목 $18.62~186.24다. 같은 평균 토큰 가정을 재시도 포함2,784회에 적용하면 입력14,976,000·출력3,552,000 토큰, 가정 비용 $32.74~327.36이다. 이는 호출 횟수 상한에 평균 길이를 곱한 민감도이며 청구액의 엄격한 상한은 아니다. 실제 중계 단가·재시도·추론 토큰에 따라 달라져 $200 이내라고 보장하지 않는다. 기존 PoC 예산을 새 검증 예산으로 자동 승계하지 않는다. 실행 전 개발/보류별 dry run에서 단가 확인 여부와 지출 상한을 기록하고, 확인 불가능하면 비용 미확인 상태를 유지한다. 구독 사용량을 $0으로 환산하지 않는다.

실행기에는 호출2,784회·경과48시간·생성 시도당 입력32,000/출력12,000·대화 턴당 입력24,000/출력1,000·판정당 입력48,000/출력6,000 토큰의 제안 중단 한도를 둔다. 모델 제한이 더 작으면 더 작은 값이 우선이다. 정확한 tokenizer로 누적 이력과 system을 포함한 dry run을 만들고, 각 실제 요청 전 한도를 다시 확인한다. 이력 압축·잘라내기로 한도를 통과시키지 않는다. 중단 슬롯은 실패로 남긴다. 이 수치를 적용한 최대 자원량은 입력82,944,000·출력8,832,000 토큰이며 비용 상한이 확인됐다는 뜻은 아니다. 사람 검토9~14시간을 별도로 확보하고, 달러/호출/토큰/시간 중 하나라도 검증된 한도를 넘으면 해당 실행을 멈춘다.

사람 검토는 보류112장면의 전체 이력을 읽는 작업이다. 장면당2~3분이면1차224~336분, 필수32장면 이중 평가64~96분, 개발8산출물56장면112~168분, 루브릭 교정60~120분, 불일치 조정60~120분을 계획한다. 총 약9~14시간이며 실제로24턴 장면을 읽는 시간이 길면 늘어난다. 이를 숨기고 “자동 점수로 품질 보장”이라 부르지 않는다.

순서는 계약·공정 구현 → 개발 자료로 규약 교정 → 공정 동결 → 새 보류 시험·사람 검토다. 개발 비교1회가 기본 예산이며 두 번째 개발 비교까지 실행하면 별도로8산출물480응답과 생성24회·판정72회(명목576호출)가 더 든다. 개발 중2회 초과 공정 개선이나 보류 재시행은 추가 분량으로 보고하고 새 실행 계획에 포함한다. 이미지·영상·외부 수집·학습·배포는 이 추정에 없다.

## 9. 완료 조건과 이번 요청의 산출물

계획 자체는 공정 품질이 검증됐다는 증거가 아니다. 구현 완료·오프라인 통과·실제 대화 수집·사람 검토·프로필 합격을 서로 나눠 기록한다. 이전520개 검사 통과를 새 공정 품질 통과로 인용하지 않는다.

이번 요청의 완료 조건은 이 계획과 독립 서브에이전트 검토, 검토 반영 기록이다. 구현은 아직 시작하지 않는다. 기존 코드·실험 원문·보고서·미커밋 변경은 보존한다.
