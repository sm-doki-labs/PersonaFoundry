# 에이전틱 실행 계획서: 승인 반응 실행 · 관문 사전 검토 · 수정 요청 재작업

- 작성일: 2026-10-28
- 상태: 제안(D-0049). PRD v1.4 §8.11, 명세 v1.4 §7.1~§7.4, LLD v1.5 §6.6~§6.10으로 옮겼다. 구현은 LLD를 따른다. 사용자 요청 "파이프라인에 에이전틱한 로직을 주입하는게 좋아 보이는데. 병렬 수행이 많고 hil이 많아서"(2026-10-28). 수치·기본값은 모두 제안이며 §9의 결정을 받은 뒤 확정한다.
- 기준 문서: [PoC 계획서](2026-10-27-poc-plan.md), [PRD](prd.md), [상세 설계](../architecture/lld.md) §6(오케스트레이터·관문), [결정 기록](../status/decisions.md) D-0010·D-0014·D-0015·D-0035·D-0047·D-0048
- 기준 코드: main `90117bf`

## 1. 목표

사람은 워크숍 화면에서 관문 결정만 누르고, 나머지는 공장이 알아서 진행한다. 구체적으로 세 가지를 바꾼다.

1. **승인 반응 실행:** 관문이 결정되면 실행기가 바로 의존이 풀린 갈래를 시작하고, 서로 막지 않는 갈래는 동시에 돌린다. 사람이 `cfp run`이나 작업 시작 버튼을 다시 누르지 않는다.
2. **관문 사전 검토:** 관문이 열릴 때 검토 에이전트가 후보마다 추천·근거·결함을 붙여 둔다. 사람은 처음부터 따지지 않고 추천을 확인하거나 뒤집는다.
3. **수정 요청 재작업:** 사람이 수정 요청 메모를 남기면 해당 단계가 그 메모를 지시로 받아 요청한 부분만 새 판으로 다시 만들고, 같은 관문을 다시 연다.

실행 순서와 의존은 지금처럼 그래프(`pipeline/graph.py`)가 정한다. 에이전트는 관문 앞(추천)과 관문 뒤(재작업)에만 들어간다. 실행 순서를 LLM이 정하면 같은 입력에서 다른 순서로 돌 수 있고, 관문 기록·해시로 누가 무엇을 승인했는지 추적하는 구조가 흔들리기 때문이다.

## 3. 지킬 원칙

- 그래프(`STAGES`의 `deps`·`needs`·`after`·`gate`)는 바꾸지 않는다. 실행 가능 여부는 지금의 `require_deps`가 판정한다.
- 추천은 승인이 아니다. 검토 결과만으로 관문 상태가 바뀌는 경로를 만들지 않는다. 실험용 `--auto-approve`(D-0015)는 그대로 두고 검토와 섞지 않는다.
- G7a(클러스터별 판정)와 G8(블라인드 20쌍)에는 추천을 붙이지 않는다. G7a는 사람 판정 자체가 데이터의 기준이고, G8은 추천이 보이면 블라인드가 깨진다. 코드에서 거부한다(`HUMAN_ONLY_GATES`를 검토에도 적용).
- 검토 모델은 그 단계의 생성 모델과 다른 계열이다(D-0010). 지금의 `judge_model`·`vision_model` 계열 확인을 그대로 쓴다.
- 유료 호출은 사용자 지시가 있을 때만 한다. 자동 재개는 유료 공급자 단계를 시작하지 않고 "실행 확인 대기"로 둔다(§4.4).
- 관문 기록·검토 기록은 한 번 쓰면 고치지 않는다(`write_once_json`). 재작업은 새 revision이다.
- 검토나 재작업이 실패해도 관문은 그대로 사람에게 열린다. 공장이 멈추지 않는다.
- 전체 흐름 테스트는 가짜 공급자로 네트워크 없이 돈다.

## 4. 갈래 A: 승인 반응 실행기

### 4.1 상태 파일 동시 쓰기 보호

- 고칠 파일: `pipeline/state.py`
- 바꿀 것: `transition`·`set_gate`가 쓰기 전에 파일 잠금(`fcntl.flock`, 잠금 파일 `state.json.lock`)을 잡고 디스크의 최신 state.json을 다시 읽어 그 위에 변경을 적용한 뒤 저장한다. 메모리의 `self.state`도 다시 읽은 값으로 바꾼다.
- 시험(`tests/test_state_concurrency.py`): 스레드 두 개가 서로 다른 단계를 `PENDING → RUNNING → AWAITING_HUMAN`으로 각 100번씩 새 revision과 함께 전이한 뒤, 두 단계의 마지막 revision과 `attempts`가 모두 남아 있다.

### 4.2 실행 가능한 단계 계산을 따로 뺀다

- 새 함수: `pipeline/scheduler.py`의 `ready_stages(state: StateFile, runners: set[str]) -> list[str]`. 지금 `run_until` 안의 판단(이미 끝남·관문 대기·의존 미충족)을 그대로 옮긴 순수 함수다.
- 시험(`tests/test_scheduler.py`): 전체 흐름 테스트의 차례별 상태를 넣었을 때 결과가 차례 표와 같다. 예를 들어 G1 승인 직후에는 `["s2"]`, s2 승인 뒤에는 `["s3", "s5"]`, G3·G5 대기 중에 G3만 승인되면 `["s3r", "s4a", "s7"]`이다(s3r는 참고 자료 색인이 없으면 바로 SKIPPED가 된다).

### 4.3 갈래 동시 실행

- 새 함수: `pipeline/scheduler.py`의 `run_waves(ctx: Context, cid: str, opt: RunOptions) -> RunLog`. `ready_stages`가 고른 단계를 스레드 풀로 동시에 돌리고, 끝나면 다시 계산해 더 돌 단계가 없을 때까지 반복한다. s2처럼 관문 없이 자동 승인되는 단계 뒤의 s3·s5도 같은 호출에서 이어서 돈다.
- 설정: `factory.toml`에 `[orchestrator] max_parallel = 3`(제안). `1`이면 지금과 같은 순차 실행이다. `FactoryConfig`에 `orchestrator: dict` 칸을 더한다.
- 함께 고칠 것: 예산(`Budget`)은 단계 실행 함수가 따로 만들어 공유하지 않으므로 그대로 둔다. `Context`의 공급자 지연 생성만 잠금으로 감싼다(LLD §6.6). 단계 하나의 검사 실패·입력 대기는 그 단계만 멈추고 다른 갈래는 계속 돈다(D-0035 유지). `RunLog`에 단계별 시작·끝 시각을 남긴다.
- `run_until`은 `run_waves`를 부르도록 바꾸고 `--until` 동작은 유지한다.
- 시험(`tests/test_run_waves.py`): (1) 가짜 단계 실행 함수에 장벽(`threading.Barrier(2)`)을 넣어 s3와 s5가 실제로 겹쳐 돈다. (2) s4a가 검사 실패해도 같은 차례의 s7→s8은 끝까지 간다. (3) `max_parallel = 1`과 `3`의 최종 대기 관문 목록이 같다. (4) 동시 실행 중 예산 상한에 닿으면 그 뒤 호출만 거절되고 이미 끝난 단계 기록은 남는다.

### 4.4 결정 뒤 자동 재개

- 고칠 파일: `web/app.py`(결정 경로), `web/jobs.py`
- 바꿀 것: 관문 결정이 기록되면 `[orchestrator] auto_resume = true`(제안 기본값)일 때 그 캐릭터의 실행 작업을 넣는다. 이미 작업이 돌고 있으면 "한 번 더 돌기" 표시만 남기고, 작업이 끝날 때 표시가 있으면 한 번 더 돈다. 결정이 수정 요청·반려면 갈래 C의 재작업이 그 작업 안에서 돈다.
- 유료 공급자 가드: 공급자 설정에 `paid = true`가 있는 단계(예: 실제 `xai_video`·`grok_oauth` 영상, 학습 제출)는 자동 재개에서 시작하지 않고 "실행 확인 대기"로 표시한다. 워크숍에 그 단계의 호출 계획·예상 비용과 "실행" 버튼을 보여 준다. 가짜·구독·로컬 중계 공급자는 자동으로 돈다.
- SSE: 작업 시작·단계 시작·단계 끝·관문 열림을 지금의 `job`·`state` 이벤트로 보낸다.
- 시험(`tests/test_web_auto_resume.py`): (1) G1 결정 POST 하나로 s2·s3·s5가 돌고 G3·G5가 대기 상태가 된다. (2) 작업이 도는 중 다른 관문 결정이 오면 작업이 끝난 뒤 한 번 더 돈다. (3) `paid = true` 영상 공급자 설정에서는 s5가 "실행 확인 대기"로 남고 공급자 호출이 0회다. (4) `auto_resume = false`면 지금처럼 아무 작업도 시작하지 않는다.

## 5. 갈래 B: 관문 사전 검토

### 5.1 대상과 검토 방식

| 관문 | 성격 | 검토 방식 | 모델 |
|---|---|---|---|
| G1 얼굴 | 고르기 | 외모군 공통 특징과 얼굴의 일치, 얼굴 결함, 추천 순위 | 비전 |
| G3 변형 | 고르기 | 씨앗(직업·나이·성별) 준수, 같은 상황에서의 첫 행동이 안끼리 다른지, 추천 순위 | 텍스트 |
| G4a 배경 | 고르기 | 챕터 장면 사실과 관계 단계에 맞는지, 챕터별 추천 | 비전 |
| G4b 자세 | 고르기 | 배경·장면 사실과 자세의 일치, 손·몸 결함, 챕터별 추천 | 비전 |
| G4 완성 이미지 | 고르기·승인 | 기준 얼굴 유지, 배경·자세 반영, 챕터별 걸리는 점 | 비전 |
| G5 소개 영상 | 고르기 | 첫 프레임과 메타데이터(길이·비율·첫 프레임 해시) 기준 추천 | 비전(첫 프레임) |
| G5b 동작 영상 | 고르기 | 동작별 첫 프레임·메타데이터, 시작·끝 표정 규칙 | 비전(첫 프레임) |
| G6 프롬프트 | 승인 | 기획서 칸 누락, 긴·짧은 프롬프트 사이 모순만 목록으로 | 텍스트 |
| G7 데이터셋 | 승인 | 표본 20개에서 말한 사람·대상·책임 소유가 뒤바뀐 곳, 요약 반복만 목록으로 | 텍스트 |
| G9 패키지 | 승인 | LLM 없이 패키지 계약·해시·빈 칸 검사 결과 요약 | 없음(결정적) |
| G7a·G8 | 사람 판정 | 검토하지 않는다 | — |

호출은 관문 하나(챕터가 있으면 챕터 하나)당 한 번으로 묶는다. 캐릭터 한 번 진행에 텍스트 3회, 비전 12회 안팎이다(G1 1, G4a 3, G4b 3, G4 1, G5 1, G5b 3). 실제 호출 전에는 지금처럼 dry run 호출 계획과 예상 비용을 낸다.

### 5.2 계약

- 새 계약 `gate-review-v1`(`contracts/review.py`): `gate`, `rev`(검토한 관문 revision), `reviewer`(공급자·모델·계열), `shownArtifacts`(본 파일 해시), `items[]`(`candidateId`, 선택 칸 `chapterId`, `rank`, `verdict`: `RECOMMEND`·`OK`·`CONCERN`, `reasons[]`, `defects[]`: `{field, note}`), `summary`, `createdAt`. 저장 위치는 `<단계 폴더>/<rev>/review-<gate>.json`, 한 번만 쓴다.
- `GateRecord`에 선택 칸 `reviewRef`(검토 기록 참조)와 `followedReview`(사람 선택이 1순위 추천과 같은지, 서버가 계산)를 더한다. 기존 기록은 칸이 없어도 읽힌다.

### 5.3 검토 실행기

- 새 파일: `pipeline/review.py`의 `review_gate(ctx: Context, cid: str, gate: str) -> Path | None`. 관문별 입력 조립과 기준표는 `REVIEWERS: dict[str, ReviewSpec]` 등록부에 두고, 프롬프트는 `prompts/review/<gate>.md`에 둔다. G7a·G8을 넘기면 `FactoryError`.
- 연결: 갈래 A의 `run_waves`에서 단계가 `AWAITING_HUMAN`이 되고 그 관문이 등록부에 있으며 `[review] enabled = true`일 때 같은 차례 안에서 검토를 돌린다. 검토가 실패하면 원장에 남기고 관문은 "검토 없음"으로 열린다.
- 설정: `[review] enabled = true`, `gates = [...]`(기본은 §5.1 표에서 G7a·G8을 뺀 전부), `vision = false`(이미지 관문 검토의 실제 호출, §9 Q1).

### 5.4 화면

- `gate_view`가 `review`(현재 revision과 맞는 검토 기록만)를 함께 돌려준다. revision이 다르면 보여 주지 않는다.
- 관문 화면: 후보 카드에 "추천"·"걸리는 점" 표시와 근거 한두 줄을 붙인다. 결정 버튼과 흐름은 지금 그대로다.

### 5.5 시험

- `tests/test_review.py`: (1) 가짜 판정 모델이 정해진 순위를 내면 `review-G3.json`이 계약대로 쓰이고 `gate_view`에 나온다. (2) G7a·G8 검토 요청은 거부된다. (3) 판정 모델이 형식이 틀린 답을 내면 관문은 `AWAITING_HUMAN`으로 남고 화면에 "검토 없음"이 나온다. (4) 검토 기록만 있고 결정이 없으면 관문 상태가 바뀌지 않는다. (5) 사람이 2순위를 고르면 관문 기록에 `followedReview = false`가 남는다. (6) 재작업으로 rev가 바뀌면 옛 검토가 화면에 나오지 않는다. (7) 생성·판정 모델 계열이 같으면 지금 규칙대로 막힌다.

## 6. 갈래 C: 수정 요청 재작업

- 넓힐 관문: G4a(챕터별 배경), G4b(챕터별 자세·장면 사실), G5(소개 영상), G6(프롬프트). G1·G4·G5b는 이미 메모를 읽으므로 공통 경로로 옮기기만 한다. G3는 화면에서 칸을 직접 고치므로 대상에서 뺀다.
- 새 계약 `rework-brief-v1`(`contracts/rework.py`): `gate`, `fromRev`, `round`, `targets[]`(`field`: 챕터·후보·동작 ID, `note`: 사람 메모 원문 그대로), `keep[]`(그대로 둘 부분), `instructions`(단계 에이전트에게 넘길 지시). 메모를 단계 지시로 바꾸는 데 텍스트 모델을 한 번 쓰고, 원문 메모는 바꾸지 않고 함께 넘긴다.
- 새 함수: `pipeline/rework.py`의 `rework_brief(ctx: Context, cid: str, gate: str) -> ReworkBrief | None`. 직전 관문 기록이 `REQUEST_CHANGES`일 때만 만든다. 각 단계 실행 함수는 `rework: ReworkBrief | None` 인자를 받아 `targets`에 든 부분만 다시 만들고 나머지는 직전 판의 파일·해시를 그대로 가져온다.
- 반복 상한: `[rework] max_rounds = 3`(제안). 넘으면 다시 만들지 않고 관문에 "반복 상한 도달"을 표시해 사람이 직접 정의하거나 반려하게 한다.
- 시험(`tests/test_rework.py`): (1) G4a에서 ch2만 수정 요청하면 새 판에서 ch2만 바뀌고 ch1·ch3 배경 해시가 같다. (2) 사람 메모 원문이 단계 에이전트 입력에 그대로 들어간다. (3) 4번째 수정 요청은 다시 만들지 않고 상한 표시를 남긴다. (4) G6 수정 요청 뒤 s8 새 판이 나오고 G6이 다시 열리며, s9s는 새 G6 승인 전까지 시작하지 않는다. (5) 반려(REJECT)는 지금처럼 메모 없이 새 판을 만든다.

## 7. 갈래 D: 대기열 정렬과 측정

- 새 함수: `pipeline/scheduler.py`의 `gate_queue(state: StateFile) -> list[QueueItem]`. 기다리는 관문마다 기다린 시간과 그 관문이 풀어 주는 뒤쪽 단계 수(그래프를 따라 전이적으로 센다)를 계산해 많이 푸는 순서로 정렬한다. 예를 들어 G3는 장면·페르소나·데이터·학습·패키지 갈래를 막아 앞에 오고, G5는 패키지 하나만 막아 뒤에 온다. LLM을 쓰지 않는다.
- 워크숍 첫 화면의 "다음에 볼 관문"을 이 순서로 보여 준다.
- 새 명령: `cfp report hil <cid>`. 관문별 검토 시간(관문 기록의 `minutes`), 수정 요청 반복 횟수, 추천 일치율(`followedReview`), 사람을 기다린 시간과 공장이 돈 시간을 표로 낸다. 결과는 `runs/characters/<cid>/reports/hil-<날짜>.json`에도 남긴다.
- 시험(`tests/test_gate_queue.py`, `tests/test_report_hil.py`): G3·G5가 함께 기다리면 G3가 먼저 온다. 전체 흐름 테스트 뒤 보고서의 관문 수가 12, G7a·G8의 추천 일치율 칸은 비어 있다.

## 12. 위험

- **동시 실행과 파일 쓰기:** state.json 말고도 단계가 공용 파일을 쓰는 곳이 있으면 덮어쓰기가 생긴다. A1 뒤 단계별 쓰기 경로를 훑어 캐릭터 폴더 밖·단계 폴더 밖에 쓰는 곳을 목록으로 만든다.
- **추천 쏠림:** Q2. 일치율과 수정 요청 횟수를 같이 본다. 일치율이 높은데 수정 요청이 늘면 추천이 틀린 쪽으로 끌고 있다는 신호다.
- **검토 비용:** 비전 검토는 관문당 호출을 늘린다. 호출 계획을 먼저 보여 주고 예산 상한(`[budget]`)을 그대로 적용한다.
- **워크숍 재시작:** 자동 재개 작업이 도는 중 서버가 꺼지면 그 단계는 `RUNNING`으로 남는다. 서버 시작 때 `RUNNING`으로 남은 단계를 찾아 다시 돌릴지 묻는 표시를 띄운다(이번 범위에서는 표시만).
