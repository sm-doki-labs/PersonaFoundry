## 1. 설계 결정

| 결정 | 내용 | 근거 |
|---|---|---|
| 단계 그래프 + 관문 | 공정을 11개 단계(S1~S11)의 방향 그래프로 정의하고, 사람 관문(G1~G9, G2는 결번)을 통과한 산출물만 다음 단계가 읽는다. 관문이 없는 자동 단계(S2·S3r)는 자동 검사를 통과한 산출물만 넘긴다(D-0042). | FR-02, FR-14 |
| 산출물 중심 | 단계 사이의 유일한 인터페이스는 파일 산출물과 그 계약(`*-v1`)이다. 에이전트의 대화 기록은 산출물이 아니라 근거 기록이다. | NFR-01, FR-34 |
| 에이전트 = 역할 + 작업 공간 + 출력 계약 | 단계 에이전트는 역할 프롬프트, 허용 도구, 작업 공간 폴더, 출력 계약으로 정의한다. 자가 검사와 재시도를 포함한 루프를 공통 러너가 돈다. | NFR-02, D-0010 |
| 생성·판정 분리 | 후보 비교, 일관성 검사, 데이터 검수는 생성 에이전트와 다른 계열의 판정 모델이 한다. 판정 결과는 관문의 참고 자료이며 승인은 사람이 한다. 사람 관문이 없는 S2 기준 사진만은 동일인 판정 통과가 곧 고정 조건이다(D-0042). | D-0010, FR-11, FR-16 |
| 공급자 포트 | 텍스트·비전·이미지 생성·영상 생성·학습·레퍼런스 출처를 포트로 추상화하고 어댑터를 설정으로 고른다. 테스트는 가짜 어댑터로 한다. | NFR-08, Q-0008 |
| 불변 revision | 고정한 산출물은 새 revision으로만 바뀐다. 같은 내용의 쓰기는 무시, 다른 내용의 덮어쓰기는 거절한다. | NFR-01, NFR-07 |
| 근거 동반 | 레퍼런스 후보·기획 칸·특질 칸은 근거(출처, 브리프 문장, 기준 문서 항목)를 함께 저장한다. | D-0004, FR-07, FR-13, FR-19 |
| dry run 기본 | 모든 명령은 호출 계획을 먼저 내고 `--execute`로만 실행한다. | D-0009, FR-03 |

## 2. 전체 구조

```
brief-v1 ──▶ Orchestrator ──▶ Stage runner ──▶ Agent runner ──▶ Provider ports
                 │                 │                │              (text / vision / image / video / tuning / source)
                 │                 │                └── workspace (runs/characters/<id>/<stage>/)
                 │                 └── automatic checks ──▶ gate record (AWAITING_HUMAN)
                 └── state.json, ledger, budget
```

구성 요소는 다음과 같다.

| 구성 요소 | 책임 |
|---|---|
| Orchestrator | 단계 그래프, 단계 상태, 관문 상태를 관리한다. 승인된 입력만 다음 단계에 넘긴다. 중단 뒤 재개한다. |
| Stage runner | 단계 하나의 입력을 모으고, 에이전트를 부르고, 자동 검사를 돌리고, 산출물을 revision으로 고정한다. |
| Agent runner | 역할 프롬프트와 작업 공간으로 모델을 부르고, 출력 계약 검증·자가 검사·재시도 루프를 돈다. |
| Checks | 스키마 검증, 규칙 검사, 판정 모델 호출(일관성·비교·검수)을 수행하고 결과를 기록한다. |
| Gates | 사람에게 보여 줄 검토 페이지와 승인·거절 기록을 만든다. |
| Providers | 외부 모델·출처 어댑터. 호출마다 원장에 기록한다. |
| Ledger·Budget | 호출·비용·사람 시간을 기록하고 실행 전 예상치를 계산한다. |
| Artifact store | `runs/` 아래 캐릭터별·단계별 폴더와 sha256 매니페스트. |

의존 관계는 다음과 같다. S1→G1→S2가 외모 축이다. S2가 외모 명세를 고정하면(사람 관문 없음, D-0042) S5(소개 영상)와 S3(씨앗 → 변형)이 갈라진다. G3 뒤 S3r, S4a, S7이 동시에 시작할 수 있다. S4a→G4a→S4b→G4b→S4→G4 순서이고, S6은 G4 승인이 필요하고 자기 관문 G5b를 갖는다(D-0033, D-0038). 오케스트레이터는 한 갈래가 관문·사람 입력을 기다리면 그 갈래만 멈추고 의존이 풀린 다른 갈래를 진행한다(D-0035). S8은 S7, S9는 S8(G6) 승인이 필요하다. S11은 G5·G8이 모두 승인돼야 한다(G5b는 R1 클립 내보내기에서 함께 묶는다). R0에서는 S6·S9~S11을 가짜 공급자로만 돌린다(D-0012).

### 3.1 에이전트 역할 요약

| 에이전트 | 역할 프롬프트의 핵심 | 허용 도구 |
|---|---|---|
| Scout | 순위 목록의 인물마다 공개 활동에서 알려진 외모를 고정 어휘로 태깅하고 확신도를 붙인다. 모르면 모른다고 쓴다. 성격을 추정하지 않고, 이름을 출력 메모에 쓰지 않는다. 군집·보고서·미리보기는 코드가 만든다. 취향 표현("예쁘다")은 근거가 아니다. | 텍스트 모델, 작업 공간 쓰기(이미지·네트워크 없음) |
| Stylist | G1에서 고른 얼굴을 참조로 기준 사진 한 장을 만든다. LLM 에이전트 없이 고정 템플릿 프롬프트와 참조 이미지 입력으로 하고, 외형 태그는 넣지 않는다(D-0043). 동일인 판정이 FAIL이면 수정 지시를 붙여 G1 얼굴에서 다시 만든다. 실존 인물을 복제하지 않는다. | 이미지 생성(참조 이미지 입력) |
| Planner | 씨앗을 지키며 상세 변형 3안을 쓴다. 안끼리는 말투가 아니라 같은 상황에서의 선택과 우선순위가 다르다. 외모 명세는 외형 묘사에만 쓴다. 페르소나 우선 경로에서는 브리프 문장을 근거로 기획 칸을 채운다. | 텍스트 모델, 작업 공간 쓰기 |

| Pose Director | 배경과 관계 단계에 맞는 자세·의상 후보를 낸다. 손은 얼굴에 닿지 않고, 영상 첫 장면으로 움직일 수 있는 자세만 낸다. | 텍스트 모델 |
| Framer | 기준 이미지의 얼굴 크롭(D-0027)과 확정된 배경 사진 두 장을 참조로 넣고, 챕터 사실과 자세·의상 문장으로 9:16 완성 이미지를 만든다. 얼굴 참조는 얼굴에만, 배경 사진은 장소·빛·배치에만 쓴다. 손이 얼굴에 닿는 자세를 막는다. 고정 템플릿이다. | 이미지 생성(참조 이미지 두 장) |

## 4. 에이전트 실행 모델

에이전트 실행 한 번은 다음 루프다(NFR-02, FR-16 재시도).

1. Stage runner가 작업 공간 폴더를 만들고 입력 산출물 사본과 역할 프롬프트, 출력 계약을 넣는다. 작업 공간 밖은 읽지 못한다.
2. Agent runner가 모델을 부른다. 출력은 계약 JSON과 선택적 첨부 파일이다.
3. 출력을 계약으로 검증한다. 실패하면 실패 사유를 붙여 다시 부른다. 연속 2회(제안) 형식 실패면 멈춘다.
4. 자동 검사를 돌린다. 실패 항목이 있으면 사유를 붙여 재생성한다. 단계별 최대 재시도 횟수(제안 3)를 넘으면 `CHECK_FAILED`로 멈추고 사람에게 보고한다.
5. 통과하면 산출물을 revision으로 고정하고 관문 기록을 `AWAITING_HUMAN`으로 만든다.

에이전트 호출은 두 방식 가운데 설정으로 고른다. API 호출(OpenAI 호환 중계)과 `codex exec` 실행이다. 후자는 파일 접근 기록을 모아 작업 공간 밖 접근이 있으면 출력을 버린다(LLD §7).

| `package_rev` | `pk<k>` | G9 승인(`release_rev` 대체, D-0044) |

브리프 하나에서 캐릭터 여러 명이 나올 수 있다. `character_id` 아래의 모든 revision은 단조 증가하며 재사용하지 않는다.

## 7. 관문과 상태 모델

단계 상태는 `PENDING` → `RUNNING` → (`CHECK_FAILED` | `AWAITING_HUMAN`) → (`APPROVED` | `REJECTED`) 이다. `REJECTED`는 사유를 받아 `RUNNING`으로 돌아가며 재시도 횟수를 센다. `SKIPPED`는 R0에서 가짜 공급자로만 돌린 단계처럼 사용자가 명시적으로 건너뛴 경우다. 관문이 없는 자동 단계(S2·S3r)는 `AWAITING_HUMAN`을 거치지 않고 자동 검사를 통과하면 바로 `APPROVED`가 된다. S2가 끝까지 검사를 통과하지 못하면 `CHECK_FAILED`로 멈추고, 사람은 다시 실행·G1에서 다른 얼굴 고르기·G1 얼굴 그대로 쓰기(`picked`) 가운데 하나를 고른다(D-0042, D-0043).

관문 기록은 `gate-record-v1`이다. 사람이 보는 검토 페이지는 정적 HTML 한 장으로, 서버 없이 열리고 결정을 JSON 텍스트로 복사하게 한다(LLD §6.4). 관문별 결정 종류는 다음과 같다.

| 관문 | 결정 | 효과 |
|---|---|---|
| G1 | 얼굴 한 장 선택(외모군은 그 얼굴에서 정함), 다시 만들기(고칠 점 메모, 같은 근거로 얼굴 미리보기만 새로), 범위·목록 수정(S1 전체 재실행) | 고른 얼굴과 그 외모군의 공통 특징만 S2 입력. 외모를 고르는 사람 관문은 G1 하나다(D-0042, D-0043) |
| G2 | 결번(D-0042). 사람 결정이 없다 | S2가 동일인 검사를 통과하면 외모 명세를 고정하고 `appearance_rev`를 발급한다 |
| G3 | 변형 한 안 선택(칸 수정 가능), 직접 쓴 안 정리본 선택, 수정 요청 | `plan_rev` 고정(D-0033) |
| G4a | 챕터마다 배경 후보 선택 또는 한두 줄로 직접 정의, 재생성 요청 | 고른 배경으로 S4b가 챕터 사실을 쓴다 |
| G4b | 챕터마다 자세 선택, 직접 정의, 고른 자세의 세부 칸 수정, 재생성 요청. 챕터 사실도 함께 검토 | `pose-plan` 고정 |
| G4 | 챕터마다 승인, 챕터별 한 줄 수정 요청(요청한 챕터만 재생성) | 승인된 이미지만 S6 입력 |
| G5 | 소개 영상 후보 하나 선택, 재생성 요청(S5) | 승인된 영상만 다음 단계와 매니페스트 입력(FR-37) |
| G5b | 동작마다 후보 하나 선택 또는 제외, 동작별 한 줄 수정 요청(요청한 동작만 재생성), 전체 거절(S6, D-0038) | 챕터마다 하나 이상 골라야 승인. 승인된 동작 영상만 앱 클립 세트 입력(FR-43) |
| G6 | 승인, 수정 요청(특질·프롬프트 칸 지정) | `persona_version` 발급 |
| G7a | 클러스터별 인계안·샘플 12개 판정(채택·수정·제외)과 고칠 점 | 그 클러스터의 대량 작성 시작 |
| G7 | 표본 판정(채택·수정·제외), 비율 조정 요청 | `dataset_rev` 고정 |
| G8 | 평가 승인, 짧은 프롬프트 운영 사용 여부 | `model_binding` 채택 |
| G9 | 릴리즈 승인·보류 | `release_rev` 발급 |

### 7.1 승인 반응 실행과 병렬 (FR-44, D-0049)

실행 순서와 의존은 §3의 그래프가 정한다. 실행기는 그래프와 상태 파일만 보고 지금 시작할 수 있는 단계를 계산하는 결정적 함수를 두고, 고른 단계를 동시에 돌린 뒤 다시 계산하기를 더 돌 단계가 없을 때까지 반복한다(물결 실행). 한 번의 실행 안에서 같은 단계는 한 번만 시도한다. 동시에 도는 단계 수에는 상한이 있다(제안 3, 1이면 지금의 순차 실행). 한 단계의 검사 실패·입력 대기는 그 단계만 멈춘다(D-0035). 상태 파일은 파일 잠금 아래 디스크의 최신 내용을 다시 읽고 고쳐 쓴다.

워크숍에서 관문 결정이 기록되면 실행기가 그 캐릭터의 실행을 이어서 시작한다(자동 재개). 이미 실행 중이면 끝난 뒤 한 번 더 돈다. 워크숍이 시작한 실행(자동 재개와 사람이 누른 실행 모두)은 유료로 표시된 공급자를 쓰는 단계를 건너뛰고 "실행 확인 대기"로 둔다. 사람이 그 단계의 호출 계획·예상 비용을 보고 실행을 누르면 그때 돈다. 명령줄 `cfp run --execute`는 사람이 직접 실행한 것이므로 이 확인을 거치지 않는다. 학습 제출은 지금처럼 `--submit-training`일 때만 한다(D-0048).

관문이 열리고 결정된 시각은 원장의 관문 사건 기록에 남는다(§7.4).

### 7.2 관문 사전 검토 (FR-45, D-0049)

관문이 `AWAITING_HUMAN`이 되면 같은 실행 안에서 검토 에이전트(Reviewer)가 그 관문의 검토 자료를 읽고 `gate-review`를 쓴다.

| 관문 | 성격 | 검토 | 모델 |
|---|---|---|---|
| G1 | 고르기 | 외모군 공통 특징과 얼굴의 일치, 얼굴 결함, 추천 순위 | 비전 |
| G3 | 고르기 | 씨앗(직업·나이·성별) 준수, 같은 상황에서의 첫 행동이 안끼리 다른지, 추천 순위 | 텍스트 |
| G4a | 고르기 | 챕터 장면·관계 단계와 배경의 맞음, 챕터별 추천 | 비전 |
| G4b | 고르기 | 배경·장면 사실과 자세의 맞음, 손·몸 결함, 챕터별 추천 | 비전 |
| G4 | 승인 | 기준 얼굴 유지, 배경·자세 반영, 챕터별 걸리는 점 | 비전 |
| G5 | 고르기 | 첫 프레임과 메타데이터 기준 추천 | 비전(첫 프레임) |
| G5b | 고르기 | 동작별 첫 프레임·메타데이터, 시작·끝 표정 규칙 | 비전(첫 프레임) |
| G6 | 승인 | 기획서 칸 누락, 긴·짧은 프롬프트 사이 모순 | 텍스트 |
| G7 | 승인 | 표본에서 말한 사람·대상·책임 소유가 뒤바뀐 곳, 요약 반복 | 텍스트 |
| G9 | 승인 | 패키지 계약·해시·빈 칸 검사 요약 | 없음(결정적) |
| G7a·G8 | 사람 판정 | 검토하지 않는다 | — |

규칙은 다음과 같다. 검토 모델은 생성 모델과 다른 계열이다(D-0010). 추천은 상태를 바꾸지 않는다. 검토는 관문 revision에 묶이고, revision이 바뀌면 옛 검토를 보여 주지 않는다. 검토 기록은 단계 산출물이 아니므로 단계 revision 폴더 밖(관문 기록 옆)에 둔다. 검토가 실패하거나 꺼져 있으면 관문은 "검토 없음"으로 열린다. 이미지·영상 관문의 비전 검토는 설정으로 켜며, 판정 경로 확인(Q-0020) 전에는 꺼 둔다. 검토는 생성물을 다시 만들지 않는다(이미지 자동 검사 루프와 별개, P-16). 관문 기록(`gate-record`)은 검토 참조와, 사람 선택이 1순위 추천과 같은지를 담는다. 추천은 사람이 고르기 전에 보여 준다(D-0049 제안).

### 7.3 수정 요청 재작업 (FR-46, D-0049)

관문 결정이 `REQUEST_CHANGES`면 그 단계는 `REJECTED`가 되고, 실행기는 다시 돌리기 전에 메모를 `rework-brief`로 정리한다. 여기에는 사람 메모 원문, 대상 부분, 그대로 둘 부분, 단계 에이전트에게 줄 지시, 반복 차수가 들어간다. 단계는 대상 부분만 새 revision으로 다시 만들고, 나머지는 직전 revision의 파일을 해시 그대로 가져온다. 대상 관문은 G1(얼굴 미리보기, D-0043), G4a, G4b, G4, G5, G5b, G6이다. G3는 화면에서 칸을 직접 고치므로 뺀다. 같은 관문의 수정 요청이 상한(제안 3)에 닿으면 실행기는 다시 만들지 않고 "반복 상한"으로 표시하며, 사람이 한 번 더 허락하면 그때 돈다. 반려(`REJECT`)는 지금처럼 메모 없이 새 revision을 만든다.

### 7.4 대기열과 사람 시간 (FR-47, D-0049)

기다리는 관문은 그래프를 따라 그 관문이 풀어 주는 뒤쪽 단계 수가 많은 순서, 같으면 오래 기다린 순서로 보여 준다. 이 순서는 결정적이며 LLM을 쓰지 않는다. `hil-report`는 관문별·revision별로 열린 시각, 결정 시각, 대기 시간, 사람이 적은 검토 시간, 결정, 수정 반복, 추천 일치 여부를 담는다. 관문 기록·상태 파일·원장만으로 다시 만든다.

## 8. 레퍼런스 선별 프로토콜 (FR-04~FR-09, FR-35, FR-36, D-0004, D-0017)

S1은 이미지를 모으지 않는다. 화제성 순위가 "누가 인기 있는가"를, 텍스트 모델의 인물 지식이 "그 사람들이 어떤 외모 계열인가"를 맡고, 공장은 여러 명이 공유하는 특징만 다음 단계로 넘긴다.

1. **범위와 목록 고정(FR-04).** 비교 범위(캐릭터 성별·연령대·그림체·인물 인상·분위기 힌트)와 순위 목록(출처·분류·기간·순위·이름)을 `popularity-ranking-v2`로 받아 해시와 함께 고정한다. 비교는 같은 범위 안에서만 한다.
2. **인물 묶기(FR-05).** 여러 목록에 같은 이름이 있으면 한 사람으로 묶고 목록별 순위를 모두 남긴다(`ranking-people-v1`). 이 파일과 순위 목록만 이름을 담는다.
3. **특징 추출(FR-06).** Scout가 인물마다 공개 활동에서 알려진 외모를 고정 어휘로 태깅하고(`appearance-features-v1`) 필드별 확신도를 붙인다. 모르는 인물은 `recognized=false`로 두고 군집에서 뺀다. 성격은 추정하지 않는다(D-0005).
4. **인기 정규화(FR-08).** 순위를 같은 목록 안의 백분위로 바꾼다. 목록이 너무 짧으면 "정규화 불가"로 표시한다. 여러 목록에 있는 인물은 가장 높은 백분위를 쓴다.
5. **군집(FR-07).** 확신도로 가중한 태그 벡터로 외모군 후보를 만든다. 공통 특징은 구성원 과반이 가진 태그다. 구성원이 기준(기본 3명) 미만이거나 공통 특징이 너무 적은 외모군은 후보에서 빼고 사유를 남긴다.
6. **근거와 한계.** 후보마다 구성원 수, 목록 수, 백분위 요약, 공통 특징을 `reference-report-v2`에 쓴다. 보고서는 "화제성 순위를 외모 인기의 대리 지표로 씀", "특징은 모델 기억에서 옴", "활동·팬덤 효과 미분리"를 항상 주의점으로 담는다. 근거가 빠진 후보는 G1에 올리지 않는다.
7. **얼굴 미리보기(FR-36).** 후보마다 공통 특징과 비교 범위(인물 인상 포함)만으로 이미지 생성 프롬프트를 만들어 얼굴 미리보기 N장(제안 1, D-0043)을 생성한다(`reference-preview-v1`). 피할 것 목록에 연예인·닮음 같은 말을 넣지 않는다. 인물 인상과 함께 쓰면 이미지 안전 시스템이 생성을 막았다(D-0020).
8. **이름 분리(FR-35).** 보고서·외모군·미리보기 프롬프트에 순위 목록의 이름이 있으면 실패한다. 프롬프트 검사는 이미지 호출 전에 한다. 닮음 여부는 따로 거르지 않는다(D-0017).
9. **G1(FR-09).** 사람이 검토 페이지에서 외모군별 얼굴과 근거를 보고 얼굴 한 장을 고른다. 고른 얼굴과 그 외모군의 공통 특징만 S2 입력이 된다. 다시 만들기를 요청하면 같은 특징·군집으로 얼굴 미리보기만 새 rev에 다시 만든다(D-0042, D-0043).
10. **검증(R2).** 서비스 썸네일 비교 결과를 외부 지표 파일로 import해 후보별 클릭률·대화 시작률을 붙인다(Q-0012).

재현성: 같은 특징 태그와 같은 설정이면 군집은 항상 같다. 특징 추출을 다시 하면 모델 응답이 달라질 수 있으므로 이전 실행과의 군집 일치도(ARI)를 보고서에 남긴다.

## 9. 외모 일관성과 이미지 자동 검사 프로토콜 (FR-12, FR-16, FR-18, FR-42, Q-0011)

`appearance-spec-v1`은 외모군 특징 태그와 그 설명, 기준 이미지(S2 기준 사진, `picked` 모드면 G1 얼굴), G1에서 고른 얼굴, 금지 요소로 이루어진다(D-0023, D-0042). 이후 생성 요청에는 기준 이미지를 참조 이미지로 넣고, 외형은 텍스트보다 참조 이미지를 따르게 한다. 같은 요청에 외형 태그를 함께 주면 모델이 글을 따라 머리색·머리 모양을 바꾸는 것을 확인했다(2026-10-21). 항목별 텍스트를 비전 모델로 보강하는 것은 나중에 한다.

검사는 세 층이다. 첫째, 판정 비전 모델이 항목별로 `MATCH`·`MISMATCH`·`UNSURE`를 내고 이유를 적는다. 둘째, 선택적으로 얼굴 임베딩 유사도를 계산해 참고 수치로 붙인다(임계값은 제안이며 단독 판정 근거로 쓰지 않는다). 셋째, 관문에서 사람이 확인한다(S2는 사람 관문이 없어 첫째 층이 고정 조건이고, 사람은 G4 완성 이미지에서 얼굴을 다시 본다). `MISMATCH`가 하나라도 있으면 사유를 붙여 재생성한다. 영상은 샘플 프레임(시작·중간·끝과 N초 간격)에 같은 검사를 적용하고 손 형태·루프 이음새를 추가 항목으로 본다.

**이미지 자동 검사·수정 루프(D-0036, D-0037).** 첫 구현은 위 첫째 층을 S4a·S4b 배경 사진과 S4 완성 이미지에 붙인 평가자–최적화자 루프다. (1) 이미지를 만든다. (2) 비전 판정 모델이 기준표의 항목마다 `PASS`·`FAIL`·`UNSURE`와 이유, FAIL이 있으면 영어 수정 지시를 낸다(`vision-verdict-v1`). 완성 이미지는 후보, 얼굴 참조, 배경 사진을 이 순서로 함께 보고 판정한다. (3) FAIL이 있으면 직전 이미지를 참조로 붙이고 수정 지시만 반영하도록 편집을 요청한다(처음부터 다시 생성하는 방식도 설정으로 고를 수 있다). (4) 상한(제안 2회 수정, 최대 3번 시도)까지 반복한다. 끝까지 통과하지 못하면 FAIL이 가장 적은 시도(같으면 나중 것)를 고르고 FAIL로 표시한 채 관문에 올린다. 단계는 실패시키지 않는다. 사람은 관문 페이지에서 통과 배지 또는 "사람 확인 필요" 경고와 이유를 보고 판단한다. 시도마다 이미지·판정·수정 지시를 `image-qa-v1`로 남긴다. 판정 모델은 생성 모델과 다른 계열이어야 하고(D-0010), 실제 이미지 공급자인데 판정 공급자가 없으면 실행 전에 거절한다. 얼굴 임베딩(둘째 층)은 아직 붙이지 않는다.

**S2 동일인 검사(D-0042, D-0043).** 같은 루프를 S2 기준 사진에 붙이되 세 가지가 다르다. (1) 기준표는 `identity-v1`(G1 얼굴과 같은 사람, 머리색·머리 모양 유지, 손이 얼굴에 닿지 않음, 인물 한 명, 글자·워터마크 없음)이고, 판정은 기준 사진과 G1 얼굴을 이 순서로 함께 본다. (2) FAIL이면 직전 이미지를 편집하지 않고 수정 지시를 붙여 G1 얼굴에서 다시 만든다. 어긋난 얼굴을 고치면 차이가 쌓이기 때문이다. (3) 상한(제안 3번 시도)까지 통과하지 못하면 가장 나은 시도를 넘기지 않고 `CHECK_FAILED`로 멈춘다. 뒤에 사람 관문이 없어서다. 판정 공급자가 없거나 자동 검사가 꺼져 있으면 `generate` 모드는 실행 전에 거절하고, 사람이 `picked` 모드(G1 얼굴을 그대로 기준 이미지로 고정, 이미지 호출 없음)를 명시해야 진행한다.

## 10. 페르소나 프로토콜 (FR-19~FR-29, D-0005~D-0007)

### 10.1 특질 시트

입력은 승인된 `character-plan`과 기준 문서다. 기준 문서는 `gemini-sft-poc`의 [선택 학습 기준](/Users/johnhuh619/projects/gemini-sft-poc/docs/research/character-factory-choice-learning-2026-10-01.md)(5항목)과 Stanford 프리셋의 카드 구조(7요소)다. 시트는 두 틀을 모두 채우고, 상황별 변화는 "조건 → 반응 → 복귀·전환 조건"으로 쓴다. 성격 형용사만 적힌 칸은 검사에서 실패한다. 참조한 SNS 14유형 ID, Stanford 프리셋 ID와 schema 버전을 기록하고, 둘 사이의 대응은 사용자가 정한 표가 있을 때만 쓴다(Q-0005).

### 10.2 긴·짧은 프롬프트

2026-10-29 보완(FR-21): S8은 승인 기획과 특질 시트를 함께 받는다. 신원·생활·기획 말투 예시·챕터를 정본에서 직접 조립해 두 프롬프트에 보존한다. 자기 일정·취향·현재 행동은 설정과 이력에 모순되지 않을 때 생성·유지할 수 있지만, 사용자 사실·공동 과거·합의·실시간 조회 결과는 근거 없이 만들지 않는다. 선택 규칙은 해당 조건에서만 쓰며 모든 대화를 약속·경계·보류로 바꾸지 않는다. 짧은 프롬프트 상한 때문에 정본을 임의 절단하지 않는다.

섹션 구성은 현행 운영 프롬프트와 같게 두고 내용만 줄인다(`gemini-sft-poc` 짧은 페르소나 정렬 원칙). 긴 프롬프트는 현행 시스템 규칙 원문(Q-0006)과 상세 특질을, 짧은 프롬프트는 핵심 특질·말투·경계를 담는다. 검사는 섹션 이름 집합 일치, 길이 상한, 금지 표현이다. 브리프의 말투 확인 문장으로 두 프롬프트의 응답 표본을 만들어 G6에 함께 보여 준다. 짧은 프롬프트는 G8을 통과하기 전까지 "운영 미채택"으로 표시한다(D-0006).

### 10.3 데이터 (R1)

재료는 세 가지다. SNS 재작성은 `gemini-sft-poc`가 만든 유형별 후보 대화를 읽기 전용으로 가져와 D-0007 규칙으로 캐릭터 턴만 다시 쓴다. NIKL은 장면·멀티턴 보강 재료다. 합성 장면은 특질 시트의 상황별 변화와 전환 조건을 덮도록 생성한다. 혼합 비율은 설정값이며 기본값이 없다(Q-0007). 각 예시는 출처·재료 종류·규칙 검사 결과를 가진다. 분할은 원본 대화 단위로 하고 평가 분할은 학습 예시 생성에 쓰지 않는다. 한국어 구어 검수는 `gemini-sft-poc`의 [대사 생성·검수 기준](/Users/johnhuh619/projects/gemini-sft-poc/docs/guides/korean-dialogue-authoring-2026-10-02.md)을 공통 문구로 포함한다.

### 10.4 SFT와 비교 평가 (R1)

학습 입력의 `systemInstruction`은 짧은 프롬프트 형식이다(FR-28). 학습 설정은 공급자가 실제로 적용한 하이퍼파라미터를 기록한다. 평가는 사전 등록 파일을 먼저 고정하고, 같은 평가 여정에서 "긴 프롬프트 + 기본 모델"과 "짧은 프롬프트 + SFT 모델"을 블라인드 짝으로 비교한다. 판정 모델의 짝 판정은 정순·역순 두 번 읽어 합의한 것만 세고, 사람 판정이 최종이다. 결과가 기준에 못 미치면 긴 프롬프트 운영을 유지한다.

## 14. 보안과 격리 (NFR-02, NFR-05, NFR-06)

- 영상 웹 어댑터(${T}grok_web${T})는 사용자가 한 번 로그인한 전용 Chrome 프로필만 쓴다. 비밀번호를 다루지 않으며, 사용자의 기본 Chrome 프로필에는 붙지 않는다. xAI 이용 정책의 자동화 금지에 걸리므로 계정 정지 위험을 감수한다는 설정이 있어야 켜진다(D-0029). API 키는 환경변수 이름(${T}XAI_API_KEY${T})으로만 받고 결과 URL을 내려받을 때는 키를 보내지 않는다.

- 에이전트 작업 공간에는 입력 사본만 둔다. 다른 캐릭터의 자산, 레퍼런스 원본 폴더 전체, 비밀값은 넣지 않는다.
- 레퍼런스 원본과 SNS·NIKL 원문은 `runs/` 또는 사용자가 지정한 외부 경로에만 둔다. 문서·보고서에는 메타데이터와 해시만 적는다.
- 원본 화자의 이름·장소·관계 등 사실이 캐릭터 설정·대사에 들어갔는지 S9 검사가 확인한다.
- S1 작업 공간에는 순위 목록의 이름·분류만 넣는다. 이름은 `ranking.json`·`people.json`·Scout 작업 공간·G1 검토 페이지에만 남고, 그 밖의 S1 산출물과 이미지 생성 요청에는 들어가지 않는다(FR-35).

## 16. 페르소나 기본 품질 공정(2026-10-29, FR-21·23·48·49)

선택한 형성 프로필에서 S7은 승인 기획을 받아 특질 호환 본문과 행동·목소리 설계를 한 호출로 만들고, 별도 writer가 정본 본문과 설계로12개 다중 턴 예시를 만든다. 형식 재시도만 최대2회 허용하고 의미상 재추출은 하지 않는다. S8은 모델 호출 없이 정본·설계·결정적4예시를 long으로 조립한다. 프로필·범위·버전 해시는 산출물에 고정한다. 기존 공정은 별도 legacy 프로필로 보존한다.

불변 신원은 정본을 따른다. 변경 가능한 일정·합의·관계 상태는 실제 이력에서 확인된 최신 변경이 정본 초기값과 예시에 우선한다. 예시 사용자 사실은 example-local이며 실제 이력이 아니다. 예시 작성 모델에 평가 문제를 주지 않는다.

새 prompt-pair-v2는 long 필수·short 선택과 상태를 구분한다. short 필수인 S9 학습 경로는 이유를 내고 멈추며 long 전용 패키지 경로는 학습을 강제하지 않는다. G6 승인 기록은 정확한 S7 revision·bundle·pair를 묶는다. 후속 단계는 승인된 버전을 읽으며 최신 trait를 임의 참조하지 않는다. 구형 v1은 그대로 읽는다.

품질 검증은 생성 공정과 별도 실행으로 둔다. 개발4캐릭터와 독립 보류8캐릭터×2회 제안, 각7장면60응답, 첫 결과 보존,16슬롯 사전 등록·실패 분모 유지가 기본 규약이다. 기획에서 봉인한 기대 행동과 실제 이력을 기준으로 판정한다. 사람이 없으면 METRICS_ONLY, 미실행은 NOT_RUN, 미달/독립성 결손은 NOT_QUALIFIED이며, 완전한 독립 사람 검토와 동결 프로필 근거를 충족할 때만 QUALIFIED다.

생성·실제 대화·기계 검사·LLM 결함 분류·사람 검토·프로필 합격을 서로 구분한다. 모델/토큰/시간/비용 한도와 실제 공급자 여부를 기록하며 합성 시험은 실제 품질 근거가 아니다. 이 절은 v1.6 개정 이력이며 [계획](../product/2026-10-29-persona-quality-floor-plan.md)의 제안 수치는 개발 단계에 교정한다.

## 17. 선택·말투 분리 형성(FR-50~53, D-0062)

새 opt-in 프로필은 `ko-text-choice-voice-long-v2`다. S3는 요구 목록→후보/선택 근거→다른 계열 의미 검토를 저장하고 G3에서 대상과 근거를 승인한다. 복수 후보의 첫 번호 자동 승인은 허용하지 않는다. 사용자 편집은 원문과 대체 관계를 보존한 새 기획 revision에서 재검토 후 기존 G3를 다시 연다. v1 동작은 유지한다.

S7은 승인 선택을 읽어 특질/blueprint-v2→12개 내용 뼈대→바인딩한 말투 렌더링→다른 계열 보존 검토를 수행한다. 출처·승인·버전이 없는 말투 자료는 READY가 아니다. 의미 실패는 재생성하지 않으며 형식만 최대 2회 재시도한다. S8은 결정적 커버리지 선정으로 4예시와 정본을 8,000자 long에 조립하고 넘으면 실패한다.

새 bundle은 원천·모델·프롬프트·계약·검사·선정 정책의 해시를 고정한다. G6/후속 소비는 정확한 묶음을 검증하고 완료 단계 재개도 stageFingerprint가 같아야 한다. 실제 대화는 기존 단일 응답·누적 이력 계약을 유지한다. short·학습은 별도 경로다.

생성·검토·소비는 영속 공유 예산으로 예약/정산하고 미확인 단가를 0으로 취급하지 않는다. 개발 A~D는 선택과 뼈대를 공유하는 불변 대조이며 정식 합격을 출력할 수 없다. 원본 대화·파생 계보를 검사하고 평가자에게 정본/설계/비주입 말투 참조를 제공한다. 사람·exact tokenizer·독립 보류 조건은 기존 정식 합격 조건을 유지한다.

## 18. 저작 행동 추천과 제작자 선택(FR-54~57, D-0066)

기본 프로필을 쓰는 단계 앞에 optional 추천을 둔다. 입력은 personality와 기본 신원·배경이고 추천은 저작 카탈로그의 행동을 반환한다. 제작자는 추천을 생략하거나 검색하고 추가·해제할 수 있다. 추천 결과와 선택 정본을 구분하며, 추천이 자동으로 캐릭터에 들어가지는 않는다.

`CreatorTrait`는 traitId, literal behavior, presetId, sourceField, catalogSha256와 sourceCatalogSha256를 가진다. `plan-seed-v1`와 `character-plan-v2`의 optional selectedTraits는 이 목록이며 기본값은 빈 목록이다. 기존 데이터는 그대로 읽힌다. 출처는 48개 허구 저작 프리셋의 expression_focus 투영이며 측정된 개인 특질·성격 점수가 아니다. SNS 검색 인덱스는 이번 카탈로그에 포함하지 않는다.

씨앗 저장은 명시적 ID를 현재 카탈로그에서 해석하고 출처를 확인한다. 기존 revision은 유지하며 예상 seedRev와 배타 잠금으로 오래된 화면과 동시 쓰기를 거절한다. 캐릭터 상태가 실행/검토/승인 중이면 저장을 막는다. 저장 뒤 기존 작업 실행 화면으로 이어지며 유료 실행 확인과 G3·G6를 우회하지 않는다.

S3는 모든 후보의 selectedTraits를 씨앗으로부터 직접 결합한다. 선택·말투 분리 v2에서는 추가 행동마다 고정 요구를 만들고 의미 검토의 입력으로 넘긴다. S7은 해당 행동을 일상/상황 성향으로 확장하며 S8은 본문을 생성 모델이 누락해도 선택 행동 원문을 disposition에 결합한다. 무조건적인 상투 반응이나 실제 이력 없는 약속을 만들지 않는 적용 규칙을 함께 넣는다. 자연스러운 대화 구현과 조합 적합성은 별도 실제 검증 대상이다.


## 19. 현행 서비스 섹션을 따르는 actor projection(FR-21·50~53)

내부 기획·선택 규칙·말투 원천과 실제 actor prompt를 분리한다. S8 새 compiler는 승인 기획·특질 시트·개인별 말투를 facts/lifeAndTastes/disposition/wantsAndFears/readingAndTension/choices/voice/boundaries 여덟 섹션에 투영한다. 특질 원문은 성격 문장이며 disposition 안에 통합하고 출처 메타정보를 표시하지 않는다. 선택은 우선순위의 경향으로 표현하며 activeWhen·firstMove·규칙 ID 등 내부 필드를 출력하지 않는다.

예시·세 챕터·영문 상태 전이표는 runtime에 넣지 않는다. 현재 관계·장면·말높임은 하나의 선택적 RuntimeContext로 받고 실제 이력의 변경을 따른다. 소유권·합의·현재 사실 경계는 공통 대화 규칙으로 간결하게 전달한다. 기존 compiler v2와 예시 선정은 과거 재현/내부 검토용으로 유지한다. 새 compiler version과 examplesUsage로 실제 예시 주입 부재를 명시한다.

v1.9 변경. 현행 서비스 참고는 로컬 활성 v6/frame v40이며 운영 DB 발행까지 확인한 뜻은 아니다. 정식 품질 기준은 완화하지 않는다.

## 20. 텍스트 모델 덱과 전환(FR-58~60, D-0072)

기준 덱 snapshot의 아홉 task에 실행 프로필을 적용하고, 선택한 호출 경로의 모델 ID 매핑을 마지막에 적용한다. 개발 기본값은 opencodex/basic_test다. 별도 test 경로는 주소와 인증 환경변수 이름을 설정한 뒤 명시적으로 선택한다. 전송 실패는 모델/경로를 바꾸지 않는다.

표준 S3는 제약 추출·Gemini 초안·독립 충돌 검토·Gemini 최종 말투를 연결하고, S7은 확정 성격/특질을 Gemini로 저작한다. S8은 승인 문장을 결정적으로 조립한다. S9는 Gemini 작성→Terra 전수 검사→Sol 이견 검토, 확인된 오류만 한 번 수정·재검사한다. 기존 다른 기획 진입점·formation 프로필의 차이는 실행 안내에 명시한다.

유효 역할/모델/추론 강도/프로필/경로/덱 해시는 출처와 불변 재개 identity에 포함한다. 사람 승인·시연 최종 점검의 실증을 설정 선택이나 합성 검사로 대체하지 않는다. 자세한 범위는 [실행 안내](../guides/text-model-deck.md)를 따른다.

## 21. 시안과 실제 텍스트 공정 API(FR-61, D-0074)

기존 시안은 같은 워크숍 서버의 /studio에서 제공한다. 기존 시뮬레이터의 시간·비용·진행은 각본이며 새 패널은 모델 덱 선택과 실제 상태/출처 읽기를 담당한다. 이 연결을 전체 시안의 실제 작업 실행기로 간주하지 않는다.

선택 API는 활성 작업과 입력을 검증하고 기존 덱 해석기를 사용한다. 읽기 API는 지정한 공장 루트의 실제 캐릭터·최근 텍스트 호출·알려진 자료만 반환하고, 과거 생성 출처를 현재 모델로 바꾸지 않는다. 인증 설정은 노출하지 않는다. 자료가 없는 루트와 별도 실험 루트는 자동 합치지 않는다. 실행과 관문은 기존 워크숍을 이용한다.

## 22. 실제 공장 화면과 실행 상태(FR-62, D-0076)

기존 워크숍의 그래프·물결 실행·사람 관문·불변 revision·유료 단계 실행 확인을 단일 실행 엔진으로 사용한다. 기본 운영 화면은 실제 모드이고, 시연은 명시적으로 선택한다. 실제 모드는 서버 없이 임의 상태로 진행하지 않는다. 공정 단위·의존관계·현재 revision·관문 대기·작업 실패·기록은 서버에서 가져오며, 실제 분할과 다른 시연용 작업을 실행한 것으로 표시하지 않는다.

제작 요청은 브리프를 고정해 보관하고 작업 큐가 매 실행·재개 때 복원한다. 등록은 생성 호출과 별개다. 시작은 실제 작업 ID를 만들고, 사람 결정은 기존 관문 경로를 통해 기록한 뒤 설정에 따라 의존이 풀린 단계를 재개한다. 단계와 전체 작업의 완료를 구분한다. 알려지지 않은 시간·비용·진행률은 추정해 채우지 않는다. 현재 루트 외의 과거·실험 데이터는 자동 병합하지 않는다.

초기 로드·실행 이벤트·재접속 때 서버 snapshot을 읽으며 사건을 놓쳐도 현재 상태를 재구성한다. 후보 검토와 결정은 같은 화면의 상세 영역에 기존 관문 화면을 삽입해 재사용한다. 클릭 방지·실패 후 재조회·연결 상태·키보드·빈 목록·손상된 상태를 처리한다. 유료 공급자 호출을 수행한 품질 검증은 별도다.

v1.12 변경(2026-10-30): 실제 운영 화면과 기존 실행기의 연결 계약을 추가한다.

## 23. QLoRA 실제 학습·선택·평가 연결과 창작 인물 정책(FR-63·64, D-0077·D-0078)

학습(s10t)은 계획 → 제출 → 원격 학습 → 같은 GPU의 선별 생성 → 회수 → 체크포인트 선택 → GPU 삭제를 한 실행으로 묶는다. GPU는 임대 기록(lease)으로 관리하며, 생성 결과가 애매해도 다시 만들지 않고 같은 라벨로 찾는다. 선별 요청은 학습에서 뺀 검증 대화에서 결정적으로 뽑으므로 독립 시험이 아니라 개발 비교(development_shared_context)다. 체크포인트 선택은 결함이 나빠지지 않는 적격 구간 안에서 짝 판정 합의 승수로 하고, 같은 짧은 프롬프트의 기반 모델이 이기면 KEEP_INCUMBENT로 남긴다. 판정이 없으면 마지막 적격을 INCONCLUSIVE로 넘긴다. 쓸 체크포인트가 없으면(BLOCKED_*) binding을 남기지 않아 평가 진입점이 학습 없이 진행할지 묻는다.

평가(s10)는 SHORT_GEMMA_SFT의 binding이 실제 어댑터 폴더면 GPU를 빌려 어댑터 서버를 띄우고 SSH 포트 전달로 답을 받는다. 사전 등록은 학습하지 않은 공급자의 SFT 조건을 넣지 않으며, 짝 판정·지표·추천은 등록된 조건만 다룬다. 패키지(s11)는 채택 어댑터의 해시·기반 모델 revision·템플릿·생성 설정·선택 기록을 serving 기록으로 남긴다.

창작 인물 정책 qlora-authored-policy-v1은 클러스터(목표 비율과 출처·보호 여부), 턴 분포, 선별·개발 비교 수량, 평가 문항군과 축, 결정값, 실패 유형별 첫 개입을 담는다. S9와 S10은 이 정책을 읽기만 하고, 정책 변경은 새 버전으로 한다.

## 24. 공식 API 직접 연결과 호출 비용 기록(FR-65~69, D-0079)

### 24.1 구성 요소

공급자 포트(§11)의 `TextModel`은 그대로 두고, 그 앞뒤에 다섯 구성 요소를 둔다.

| 구성 요소 | 역할 | 만족하는 요구 |
|---|---|---|
| 호출 경로 해석기 | 덱 task의 모델을 고른 경로에 맞춰 주소·인증 환경변수 이름·공식 모델 ID·모델 계열·과금 구분으로 바꾼다. | FR-65 |
| 요청 형식 | 호출 주소의 공급자에 맞춰 요청 본문을 만들고, 응답의 사용량을 공통 형식(`usage-v1`)으로 정리하며, 거절 응답을 공급자 요청 오류로 바꾼다. | FR-66 |
| 단가표 | 모델 ID와 호출 시각으로 단가 항목을 찾고, 사용량과 단가로 비용을 계산한다. | FR-67 |
| 비용 기록 | 호출 추적 래퍼가 사용량·단가·과금 구분·잘림 여부를 원장 행에 남긴다. | FR-67 |
| 예산·보고 | 형성 실행 예산의 단가 상한을 단가표에서 정하고, 원장으로 비용 보고서(`cost-report-v1`)를 만든다. | FR-68, FR-69 |

### 24.2 호출 경로 `api`

`api` 경로는 모델 계열마다 전송 설정을 하나씩 둔다. 계열은 덱 모델 ID로 정한다. `gpt-`로 시작하면 `openai`, `gemini-` 또는 `google-antigravity/gemini-`로 시작하면 `gemini`다. 다른 모델은 계열을 정할 수 없으므로 해석 단계에서 거절한다.

| 계열 | 기본 주소 | 기본 인증 환경변수 | 공식 모델 ID 규칙 |
|---|---|---|---|
| `openai` | `https://api.openai.com/v1` | `OPENAI_API_KEY` | 덱 ID를 그대로 쓴다. |
| `gemini` | `https://generativelanguage.googleapis.com/v1beta/openai` | `GEMINI_API_KEY` | `google-antigravity/` 접두사를 뺀다. |

설정은 계열별 주소·환경변수 이름과 모델 ID 매핑을 덮어쓸 수 있다. 덮어쓴 매핑이 기본 규칙보다 우선한다. 해석 결과에는 계열과 과금 구분이 붙는다. 과금 구분은 `api` 경로가 `api_billed`(주소가 공식 호스트일 때, 아니면 `unverified`), opencodex가 `relay_equivalent`, test가 주소와 무관하게 `unverified`, 가짜 공급자가 `none`이다. 인증 환경변수 이름은 대문자·숫자·밑줄만 허용하고 키 모양 값을 거절하며, 오류 문구에 그 이름을 넣지 않는다. 경로 선택(FR-59)은 `api`를 받아들이며, 선택 전에 모든 덱 task가 해석되는지 검사한다. 키 값이 비었는지는 선택할 때가 아니라 호출 전에 검사한다. 키를 넣기 전에도 경로를 고르고 호출 계획을 볼 수 있어야 하기 때문이다. 화면 응답과 원장에는 환경변수 이름과 키 값을 넣지 않는다.

덱을 거치지 않는 `[providers.text]`·`[providers.judge]`는 기존처럼 주소와 환경변수 이름을 직접 적어 공식 API를 가리킬 수 있다. 이 경우에도 같은 요청 형식과 비용 기록을 적용한다.

### 24.3 요청 형식과 사용량 정리

요청 형식은 호출 주소의 호스트로 고른다. 그 밖의 주소(중계·테스트 서버)는 지금 동작을 그대로 유지한다.

| 형식 | 출력 상한 | `temperature` | 추론 강도 |
|---|---|---|---|
| `openai` | `max_completion_tokens` | 추론 강도가 `none`일 때만 보낸다. 추론 강도를 주지 않으면 모델 기본값(medium)이 적용되므로 뺀다. Sol에 `none`을 주면 호출 전에 거절한다. | `reasoning_effort` |
| `gemini` | `max_tokens`(Q-0025 확인 전 기본값) | 보낸다. | `reasoning_effort` |
| `generic` | `max_tokens` | 보낸다. | 설정에 있으면 보낸다. |

`usage-v1`은 `inputTokens`(캐시 읽기·쓰기를 포함한 전체 입력), `cachedInputTokens`(캐시 읽기), `cacheWriteTokens`(캐시 쓰기), `outputTokens`, `reasoningTokens`, `finishReason`, `usageSource`로 이루어진다. `outputTokens`는 청구되는 출력이다. 응답에 총 토큰이 있고 `총 토큰 − 입력 토큰`이 보고된 출력 토큰보다 크면 그 차이를 출력으로 쓰고 `usageSource`에 보정 사실을 남긴다(Q-0023). 캐시된 입력과 추론 토큰은 응답의 세부 항목에 있을 때만 채우고, 없으면 비워 둔다. 값을 모르면 0으로 채우지 않는다.

429와 5xx, 전송 오류는 기존 재시도 규칙을 따른다(덱 경로는 재시도 0회). 그 밖의 4xx는 공급자 요청 오류로 바꿔 바로 멈추며, 상태 코드와 공급자 오류 문구를 앞부분만 남긴다. 문구에 키 값이 들어 있으면 가린다.

### 24.4 단가표 `price-table-v1`

단가표는 저장소 자료 파일로 두고 버전으로만 바꾼다. 항목은 `model`, `family`, `effectiveFrom`, `effectiveTo`, `inputPerMillion`, `cachedInputPerMillion`, `cacheWritePerMillion`, `outputPerMillion`, `source`, `checkedAt`으로 이루어진다. 출력 단가는 추론·생각 토큰을 포함한다. 확인하지 못한 단가 칸은 비워 둔다. 조회는 공식 모델 ID와 호출 시각(UTC)으로 하며, 기간이 겹치는 항목이 둘이면 표 오류로 거절한다. 설정의 단가 덮어쓰기는 표 항목보다 우선하고 `basis = config_override`로 표시한다.

비용은 `(입력 − 캐시 읽기 − 캐시 쓰기) × 입력 단가 + 캐시 읽기 × 캐시 읽기 단가 + 캐시 쓰기 × 캐시 쓰기 단가 + 출력 × 출력 단가`를 100만으로 나눈 값이다. OpenAI는 1,024토큰을 넘는 요청에 캐시 경계를 자동으로 만들고 캐시 쓰기를 입력 단가의 1.25배로 청구하므로, 이 항을 빼면 입력 비용이 낮게 잡힌다. 캐시 읽기 토큰이 있는데 캐시 읽기 단가가 비어 있으면 그 부분에 입력 단가를 적용하고 상한 추정이라는 표시를 남긴다. 캐시 쓰기 토큰이 있는데 쓰기 단가가 비어 있으면 비용은 미확인이다. 입력 단가나 출력 단가가 비어 있거나 사용량을 모르면 비용은 미확인이다.

초기 적재값은 2026-11-04에 확인한 값이며 제안이다. 단위는 100만 토큰당 USD다.

| 모델 | 적용 기간 | 입력 | 캐시 읽기 | 캐시 쓰기 | 출력 | 출처 |
|---|---|---|---|---|---|---|
| `gpt-6.1-sol` | 확인일부터 | 2 | 0.10 | 2.50 | 10 | [OpenAI 요금표](https://developers.openai.com/api/docs/pricing) |
| `gpt-6.1-terra` | 확인일부터 | 1 | 0.05 | 1.25 | 5 | [OpenAI 요금표](https://developers.openai.com/api/docs/pricing) |
| `gemini-3.8-flash` | ~2026-12-31 | 0.75 | 0.075 | 미확인 | 3.75 | [Gemini 요금표](https://ai.google.dev/gemini-api/docs/pricing) |
| `gemini-3.8-flash` | 2027-01-01~ | 1.50 | 0.15 | 미확인 | 7.50 | [Gemini 3.8 Flash 안내](https://ai.google.dev/gemini-api/docs/latest-model) |
| `gemini-4-argon` | ~2026-11-30 | 2 | 미확인 | 미확인 | 10 | [Gemini 요금표](https://ai.google.dev/gemini-api/docs/pricing) |

### 24.5 원장 행과 비용 보고서

원장 행(§12)에 `cachedInputTokens`, `cacheWriteTokens`, `reasoningTokens`, `finishReason`, `usageSource`, `price`(단가표 버전·항목 기간·출처·`basis`), `billing`(경로·계열·과금 구분)을 더한다. 기존 `estCostUsd`는 계산한 비용을 담고, 미확인이면 `null`이다. 실패한 호출은 비용 없이 공급자 요청 오류의 상태 코드를 남긴다. 기존 행은 고치지 않으며, 새 필드가 없는 행은 보고서에서 과금 구분 미상으로 읽는다.

`cost-report-v1`은 원장만 읽는다. 단계·모델·과금 구분별 호출 수, 토큰, 비용 합계, 단가 미확인 호출 수, 잘린 응답 수를 담는다. `api_billed` 합계와 `relay_equivalent` 합계는 따로 보인다. 재계산 모드는 같은 단가표를 과거 행에 적용하되 결과를 원장과 다른 위치에 쓰고, 원래 원장의 비용 칸을 고치지 않는다.

### 24.6 예산 단가

형성 실행 예산(§17)의 입력·출력 단가 상한은 설정에 값이 있으면 그 값을 쓴다. 값이 없으면 지금 선택한 프로필·경로로 해석한 모든 덱 task 모델의 단가 가운데 가장 높은 입력 단가(캐시 쓰기 단가가 더 높으면 그 값)와 출력 단가를 실행 시각 기준으로 고른다. 그중 하나라도 미확인이면 호출 전에 거절한다. 예산 봉투는 처음 만든 단가로 고정된다. 재개할 때 현재 프로필·경로의 최고 단가가 봉투 단가보다 높으면 상한이 실제보다 낮게 잡히므로 거절하고 새 예산 ID를 요구한다. 형식·인증 오류로 거절된 요청의 예약은 0으로 정산한다. 기존 명령 단위 예산은 호출 계획의 비용 추정에 같은 단가표를 쓴다.

### 24.7 병렬 구현 갈래

계약(§24.2~§24.6의 필드 이름, 해석 결과, `usage-v1`, 단가 조회·비용 계산의 입출력)은 이 절로 고정한다. 각 갈래는 다른 갈래의 결과를 계약에 맞춘 가짜 구현으로 대신해 동시에 시작한다. 파일 소유와 충돌 지점은 LLD에서 정한다.

| 갈래 | 맡는 것 | 받는 계약 | 내는 계약 |
|---|---|---|---|
| A 호출 경로 | `api` 경로 해석, 계열 판정, 공식 모델 ID 매핑, 호출 전 키 확인, 경로 선택·표시(명령과 화면) | 덱 snapshot, 설정 | 해석 결과(주소·환경변수 이름·공식 모델 ID·계열·과금 구분) |
| B 요청 형식 | 형식 선택, 요청 본문, `usage-v1` 정리, 공급자 요청 오류 | 해석 결과의 주소 | 응답의 `usage-v1`, 공급자 요청 오류 |
| C 단가표 | `price-table-v1` 자료와 검증, 조회, 덮어쓰기, 비용 계산 | 없음 | 단가 조회·비용 계산 |
| D 기록·예산·보고 | 원장 행 확장, 추적 래퍼의 비용 기록, 형성 예산 단가, `cost-report-v1`, 재계산 | A의 과금 구분, B의 `usage-v1`, C의 조회·계산 | 원장 행, 보고서 |
| E 통합 | 설정 예시, `.env.example`, 실행 안내·상태 문서, 전체 회귀 검사, 독립 검토, 실제 1회 실행용 호출 계획 | A~D | 통합 결과 |

A·B·C는 서로 의존하지 않는다. D는 A·B·C의 가짜 구현으로 시작하고, 합칠 때는 C → B → A → D 순서로 넣은 뒤 E가 진행한다. 각 갈래는 자기 범위의 오프라인 테스트를 함께 낸다. 실제 공급자 호출은 E가 끝나고 사용자가 실행을 지시한 뒤에만 한다.
