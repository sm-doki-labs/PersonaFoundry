# 세션 간 인계 규칙

`docs/status/`는 세션이 바뀌어도 작업 상태·결정·질문·검증 결과가 이어지게 하는 영역이다. 현재를 보여 주는 문서 두 개와 쌓아 가는 기록 네 종류로 나뉜다.

| 문서 | 성격 | 고치는 방식 | 쓰는 시점 |
|---|---|---|---|
| [current-state.md](current-state.md) | 지금 공정이 실제로 어디까지 되는가: 단계별 현황, 사람이 처리할 일, 자료 위치, 다음 할 일 | 현재 사실에 맞춰 고친다 | 세션 종료 시 |
| [known-issues.md](known-issues.md) | 지금 안 되는 것(`K-NNNN`): 막힘·미검증·미구현·한계 | 고친다. 지우지 않고, 풀리면 해결 표로 옮긴다 | 안 되는 것을 확인했거나 풀었을 때 |
| `handoffs/handoff-YYYY-MM-DD[-topic].md` | 세션 하나의 상태 스냅샷 | 작성 뒤 고치지 않는다 | 세션 종료·중단 시 |
| [decisions.md](decisions.md) | 결정 기록. `확정`·`제안`·`폐기` 상태를 가진다 | 덧붙이기만 한다 | 결정이 생기거나 바뀔 때 |
| [open-questions.md](open-questions.md) | 사람이 정해야 할 질문. 해결되면 결정 ID를 적는다 | 덧붙이고 상태만 바꾼다 | 질문이 생기거나 풀릴 때 |
| [verification.md](verification.md) | 실제로 실행한 검증의 누적 기록 | 덧붙이기만 한다 | 검증을 실행했을 때 |

세 가지를 섞지 않는다. 사람이 골라야 하는 것은 질문(Q), 지금 안 되는 사실은 알려진 문제(K), 실제로 돌려 본 결과는 검증 기록에 둔다. 예를 들어 "Grok 사용량을 어떻게 확보할지"는 Q-0018이고, "무료 계정은 1편 뒤 결제 창이 떠서 S5가 막힌다"는 K-0001이며, 그 결제 창을 본 실행은 검증 기록의 한 줄이다.

## 인계 문서 규칙

양식은 [handoff 템플릿](../templates/handoff-template.md)이다. 다음 절을 이 순서로 둔다.

1. **지금 상태 한눈에**: 진행 중인 캐릭터·단계·관문 상태를 5줄 안에 적는다.
2. **이번 세션에서 한 일**: 산출물 경로와 함께 적는다. 실행하지 않은 것은 "실행하지 않았다"고 명시한다.
3. **결정**: 이번 세션에서 추가한 결정 ID 목록. 내용은 결정 기록에 둔다.
4. **확인한 사실과 정정**: 이전 인계와 다른 점, 잘못 알고 있던 것. 이전 문서를 고치지 않고 여기에 적는다.
5. **미결**: 새로 생기거나 남은 질문 ID(Q)와, 새로 확인했거나 풀린 알려진 문제 ID(K).
6. **다음 할 일**: 우선순위 순서. 첫 항목은 다음 세션이 바로 시작할 수 있을 만큼 구체적으로 쓴다.
7. **떠 있는 것**: 실행 중인 프로세스, 임시 서버, 외부 작업(학습 job 등), 임시 파일. 없으면 "없음".

지켜야 할 표현 규칙:

- 제안한 수량·모델·임계값은 "제안"으로 적는다. 사용자 확정은 결정 ID로만 표시한다.
- "완료"는 산출물 경로 또는 검증 기록 항목이 있을 때만 쓴다. 로그인·설치·연결 응답만으로 동작을 확인했다고 쓰지 않는다.
- 다른 세션이 병렬로 진행한 작업은 "확인만 함"으로 구분한다.
- 비밀값, 개인 계정 정보, 수집한 원본 화자의 개인 사실을 적지 않는다.

## 결정 기록 규칙

한 항목은 `D-NNNN` ID, 날짜, 상태, 결정, 근거, 고려한 대안, 영향받는 문서로 이루어진다. 상태는 세 가지다.

| 상태 | 뜻 |
|---|---|
| `확정` | 사용자가 직접 정했거나 사용자가 제시한 원칙이다. 사용자 지시 없이 바꾸지 않는다. |
| `제안` | 에이전트가 작업을 진행하기 위해 택한 기본값이다. 사용자가 확정하거나 바꿀 수 있다. |
| `폐기` | 더 이상 유효하지 않다. 대체한 결정 ID를 적는다. |

항목을 지우거나 내용을 고치지 않는다. 바뀌면 옛 항목의 상태만 `폐기`로 바꾸고 새 항목을 덧붙인다.

## 미결 질문 규칙

한 항목은 `Q-NNNN` ID, 날짜, 질문, 영향받는 단계·문서, 현재 기본 가정, 해결 상태(`열림`·`해결 D-NNNN`)로 이루어진다. 기본 가정이 있으면 그 가정으로 작업을 진행하되 결과물에 가정을 표시한다.

## 노드 성숙도 규칙

공정은 골격을 먼저 깔고 노드마다 실제로 확인하며 올린다. 노드(단계와 그에 딸린 관문·검사)마다 다음 단계 가운데 하나를 매긴다.

| 단계 | 뜻 | 올리는 조건(근거) |
|---|---|---|
| L0 설계 | PRD·명세·LLD에만 있다 | 문서 |
| L1 골격 | 가짜 공급자로 입출력·관문·상태가 이어진다 | 오프라인 테스트 통과 |
| L2 실제 1회 | 실제 모델·서비스로 한 번 돌아 산출물이 계약에 맞고 다음 관문까지 간다 | 검증 기록 한 줄과 산출물 경로 |
| L3 품질 | 사람이 정한 기준(합격률·일치율 등)을 넘는다. 기준은 결정 기록에 둔다 | 측정 결과(검증 기록 또는 보고서) |
| L4 운영 | 반복 실행에서 비용·시간·실패 처리가 안정적이다 | 여러 번의 실행 기록과 원장 |

규칙:

1. **앞 노드가 L2 전이면 뒤 노드를 L2 이상으로 올리지 않는다.** 실제로 돌린 앞 노드의 출력이 있어야 뒤 노드의 실제 실행이 의미가 있다. 가짜 입력으로 만든 L1 골격은 언제든 깔 수 있다.
2. 단계를 올릴 때는 근거를 [검증 기록](verification.md)에 남기고 [현재 상태](current-state.md)의 표를 고친다. 근거 없이 올리지 않는다.
3. 실제 실행에서 계약을 바꿔야 할 문제가 나오면 그 노드와 그 출력을 쓰는 뒤 노드를 L1로 내린다. 계약을 고치고 다시 L2를 확인한다.
4. 노드 일부만 실제로 확인했으면(예: 어댑터 호출만, 첫 프레임만) 단계를 올리지 않고 현재 상태 표의 비고에 적는다.
5. 관문 결정을 자동 승인(`--auto-approve`, D-0015)으로 넘긴 실행도 L2 근거가 될 수 있다. 다만 검증 기록에 자동 승인임을 적고, 사람 선택이 품질 판단에 필요한 L3 근거로는 쓰지 않는다.

## 알려진 문제 규칙

한 항목은 `K-NNNN` ID, 분류(`막힘`·`미검증`·`미구현`·`한계`), 단계, 안 되는 것, 근거, 영향, 풀리는 조건·다음 행동, 관련 Q·D ID로 이루어진다. 코드가 있어도 실제로 돌려 보지 않았으면 `미검증`으로 적고 "된다"고 쓰지 않는다. 우회가 있으면 함께 적는다. 풀린 항목은 지우지 않고 "해결된 항목" 표로 옮겨 해결 근거(결정 ID나 검증 기록 날짜)를 적는다. [현재 상태](current-state.md)의 단계별 표는 K ID로 이 문서를 가리킨다.

## 검증 기록 규칙

한 항목은 날짜, 실행한 명령 또는 절차, 입력 revision, 결과(통과·실패와 수치), 결과 파일 경로다. 네트워크 없는 오프라인 검증과 실제 외부 공급자를 부른 검증을 구분해 적는다.
